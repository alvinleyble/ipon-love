# Sync cursor model: dirty-flag push, server-assigned `server_rev` pull

**Context.** Because `updated_at` is client-stamped (ADR-0001), it cannot safely double as a change-detector. Selecting pushes by `updated_at > last_sync` can skip freshly edited rows whose timestamp is behind the cursor (and re-pushes just-pulled rows); selecting pulls by `updated_at > last_sync` silently and permanently loses a partner's edit that was authored before the cursor but arrives at the server after it (the "late arrival below the high-water mark" bug — acute in the couples case where one partner syncs while the other is offline). The author's edit time and the server's receipt order are different orderings, and client clocks make them diverge.

**Decision.** Split selection from conflict resolution, and use the right ordering for each side.
- **Push (outbox):** every syncable Room row carries a local-only `pending_sync` boolean, set on each local write and cleared on a successful push ack. Push selects `pending_sync = true` — no timestamp math. `pending_sync` is never sent to Supabase.
- **Pull (change marker):** every syncable table carries a server-assigned `server_rev bigint`, drawn from one global Postgres `SEQUENCE` via a `BEFORE INSERT OR UPDATE` trigger (which touches only `server_rev`, never `updated_at` — ADR-0001's no-trigger rule on the LWW key stands). The pull cursor is the max `server_rev` seen, stored **per table** in DataStore. Pull selects `server_rev > cursor` and advances to the max received, so late-arriving old edits get a fresh-high `server_rev` and are fetched correctly.
- **Conflict:** when a row is both locally dirty and newer remotely, `updated_at` (LWW) decides the winner. `server_rev` only decides what is new to fetch.

**Consequences.** A single global sequence gives a total receipt order across tables; a per-table cursor keeps a large/slow table from starving a small one. Cost is one sequence, one trigger function applied across ~8 tables, and a `server_rev` column each — accepted over the simpler timestamp cursor because silent loss is unacceptable for a finance app. `supabase/schema.sql` must be updated to add the sequence, trigger, and `server_rev` columns when this is implemented.
