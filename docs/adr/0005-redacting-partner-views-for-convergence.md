# Partner reads go through redacting views so removals converge

**Context.** With partner data replicated into local Room (ADR-0004), the partner's replica must be able to converge on *removing* a row, not just adding/updating one. The original `schema.sql` partner-read policies gate visibility on `is_private = false AND is_deleted = false` (and notes on `is_shared = true`). That makes the transition *into* invisibility itself invisible: when an owner privatizes, deletes, or un-shares a row, the partner can no longer read it, never receives the change, and keeps a stale copy forever — a privacy leak (a "private" transaction stays visible on the partner's phone) and a failed-delete bug.

**Decision.** Replace the raw partner-read policies with **redacting views** (`partner_transactions`, and equivalents for notes/accounts/categories). Each view: returns partner rows **regardless** of `is_private` / `is_deleted` / `is_shared` so the transition always propagates; **nulls out content columns** (amount, note, category, title, body, …) whenever `is_private` or `is_deleted` is true, so a now-hidden row crosses the wire as a content-less marker; and always exposes `id, user_id, is_private, is_deleted, updated_at, server_rev`. The sync merge treats a pulled partner row flagged private/deleted (note: unshared) as **purge the local copy**.

**Consequences.** Privacy holds — redaction is server-side, hidden content never reaches the partner's device — and the replica can finally converge on removal. Cost: partner rows are pulled from views, a second pull source per shared table, which must be kept in sync with the base-table columns. **Supersedes the `*_partner_read` policies in `supabase/schema.sql`. Rejected:** keeping the original policies (ships a finance app that leaks private rows and silently fails deletes) and per-partner tombstone rows (more machinery than a view).
