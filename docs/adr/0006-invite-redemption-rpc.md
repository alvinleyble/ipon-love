# Invite redemption via a SECURITY DEFINER RPC; `couples` joins the sync model

**Context.** Joining a couple requires an unpaired user to find a couple by its invite code and write herself into `couples.user2_id` + her own `users.couple_id`. The RLS policies gate `couples` SELECT/UPDATE on `user1_id = auth.uid() OR user2_id = auth.uid()` — but a joining user is neither yet, so she can neither look the couple up by code nor write herself in (chicken-and-egg). Separately, `couples` carries only `created_at`, so even a completed join is invisible to the pull cursor and never reaches the other partner.

**Decision.** Redeem invites through a `SECURITY DEFINER` RPC, `redeem_invite(code text)`, rather than direct table writes. Running with elevated rights, it sidesteps the chicken-and-egg and is the one place to enforce the invariants atomically: the code exists, the couple's `user2` slot is empty, the caller is not already in a couple, and the caller is not `user1` joining their own couple. It sets `user2_id` and the caller's `couple_id` in a single transaction. Invite-code generation/rotation is a sibling RPC. Additionally, `couples` gains `server_rev` and `updated_at` like every other synced table, so a completed join propagates to the other partner through the normal pull (fetching the updated couple row + the new partner's `users` row).

**Rejected:** loosening `couples` RLS to allow lookup/update by `invite_code` for unpaired users — it lets anyone enumerate or claim couples by guessing codes. The RPC keeps validation server-side. Updates `supabase/schema.sql` (new RPCs, `couples.server_rev`/`updated_at`).
