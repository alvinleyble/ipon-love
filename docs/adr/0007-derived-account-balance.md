# Account balance is derived from the ledger, not a synced field

**Context.** `accounts.balance` was a stored authoritative `numeric`, but the same number is also implied by the transactions hitting the account — two sources of truth. Under row-level LWW (ADR-0003) this drifts: two offline edits on two devices each adjust `balance`, both account rows collide on sync, LWW keeps one, and the displayed balance silently diverges from the sum of the (correctly merged) transactions. Unacceptable for a finance app.

**Decision.** Make balance derived. The account stores `opening_balance` (set at creation, rarely edited — safe under LWW because it almost never changes) instead of an authoritative running `balance`. Current balance is computed from the local transaction ledger: `opening_balance + Σ(income) − Σ(expense) ± transfers`, as a Room `SUM` (cacheable locally but never synced). Manual "adjust balance" becomes a special adjustment transaction, not a direct balance write, keeping the ledger the single source of truth.

**Consequences.** Balance can no longer be a sync casualty — transactions merge independently and the figure recomputes deterministically. It is eventually consistent (shows the balance of locally-present transactions, converging as sync completes), which beats a confidently-wrong authoritative number. Cost: a `SUM` per account. Updates `supabase/schema.sql` (`balance` → `opening_balance`). **Rejected:** keeping stored authoritative balance (drifts), and recompute-and-overwrite after sync (still stores a redundant field that can be read mid-sync in a wrong state).
