# Unpairing: shared budgets die, notes revert to owner, replicas purge on the `couple_id`-null signal

**Context.** Either partner can unpair. Setting `users.couple_id = null` alone leaves two problems: (1) once `couple_id` is null, RLS returns no partner rows, so the device can never receive per-row "purge" markers — the partner's replicated transactions/accounts/categories sit in local Room forever (a stale-data + privacy leak, the mirror of ADR-0005); (2) shared budgets are couple-owned (`user_id` null), so after dissolution they have no owner, and shared notes are owner-owned but flagged shared — both need an explicit disposition.

**Decision.** Unpair through a `SECURITY DEFINER` RPC that runs atomically: set *both* users' `couple_id = null`; **soft-delete shared budgets** (a jointly-set number neither person should inherit alone); **revert shared notes to private-to-their-owner** (`is_shared = false`, `couple_id = null`, preserving authorship — you keep your own notes, you just stop sharing); soft-delete the dissolved couple (`couples` gains `is_deleted`); bump `server_rev` throughout. Each client detects the dissolution from its **own `users` row** (always readable by its owner even after RLS cuts off partner reads) flipping to `couple_id = null`, and runs a **local bulk purge** of every replicated non-owned row (partner-owned + couple-owned) — no per-row markers required. Re-pairing is a fresh `redeem_invite` creating a new couple.

**Rejected:** handing each partner a personal copy of the shared budget (inherits a co-set number out of context) and keeping shared budgets couple-owned-but-orphaned (no owner, can't be cleaned up). Updates `supabase/schema.sql` (unpair RPC, `couples.is_deleted`).
