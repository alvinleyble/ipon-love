# Sync is FK-ordered, idempotent, and resumes per-table after partial failure

**Context.** Referential integrity spans the sync boundary (a transaction needs its account/category; note_images need their note; budgets need categories) and mobile sync dies mid-batch routinely. Applying a child before its parent breaks FKs; a connection drop mid-push or mid-pull must not lose or skip rows.

**Decision.** Three composing rules. (1) Process tables in FK-dependency order both directions — users → couples → accounts → categories → recurring_rules → transactions → budgets → notes → note_images. Because the app always creates a parent before its child and pushes in this order, a parent receives a lower `server_rev` than its child, so pulling in the same order guarantees a child's parent is already present (safety net: buffer-and-retry a row whose FK isn't yet satisfied rather than dropping it). (2) Every push and pull-apply is an upsert keyed by `id`, so redoing one is a no-op and partial failure is just "resume next cycle." (3) Advance state only after a committed write: clear `pending_sync` per row as its push ack returns; apply each table's pull batch in a Room transaction and advance that table's `server_rev` cursor only on commit.

**Consequences.** A sync is interruptible at any point and self-heals next run, with no distributed transaction. **Rejected:** applying a whole pull cycle as one all-or-nothing Room transaction — per-table commit keeps transactions small and lets progress survive a flaky connection, which matters more than cross-table atomicity given idempotent re-pull.
