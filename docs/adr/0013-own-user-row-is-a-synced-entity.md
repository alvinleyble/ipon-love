# The user's own `users` row is a normal synced entity, not a special creation path

**Context.** ARCHITECTURE.md §5 said "on verification, the app creates a row in the `users` table," but verification happens out-of-app (email link) so it isn't an observable moment, and a one-shot direct insert can fail offline at first login — stranding every FK'd row (accounts, transactions…) because the server FK to `users` is unsatisfied. The common Supabase shortcut, a trigger on `auth.users` that auto-inserts `public.users`, would race/conflict with the offline-first outbox that also wants to own that row.

**Decision.** Treat the user's own `users` row as just another synced Room entity. On first post-verification login, insert it into Room with `pending_sync = true`; the outbox creates it on Supabase, and because `users` is first in the FK push order (ADR-0009) it always lands before any referencing row. Onboarding (display name, accent color) is an edit to that row; couple creation is the `create_couple` RPC, gated behind the first successful sync so the row provably exists server-side before `create_couple` runs `update users …`. New-device login restores it via the initial full sync (cursor 0), pulled first by the same ordering. RLS `users_insert` (`id = auth.uid()`) already permits the self-insert.

**Rejected:** a one-shot direct insert (can strand FK'd data when offline), a server-side `ensure_user_row` RPC (an extra round-trip that still isn't offline-safe), and an `auth.users` trigger (the popular pattern, but it races the outbox for ownership of the row and bypasses the uniform sync path).
