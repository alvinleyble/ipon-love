# Customizable bottom navbar via a destination registry

**Context.** The bottom nav was a fixed five-tab `enum` (`TopLevelDestination`) hard-wired in `IponApp`, with every other module (Notes, Recurring, Couple, Settings, …) reachable only through ad-hoc top-bar callbacks on the Records screen. V1.3 wants users to choose which modules sit in the bar and rearrange them, with an overflow for the rest. A fixed enum can't express a user-defined, runtime-mutable, paired-aware set.

**Decision.** Introduce a **destination registry** — a single list of nav-able destinations, each with `id`, `label`, `icon`, `route`, and `requiresPaired`. The bottom bar is built dynamically from a stored config: **up to 4 user-pinned, reorderable destinations + an always-present "More"** as the last item (min 1 pin; the first pin is the `NavHost` start destination). Default pins: Records, Analysis, Couple, Budgets. "More" opens a modal bottom-sheet grid of all currently-visible modules plus an "Edit navbar" entry (drag-to-reorder / pin / unpin); the editor is also linked from Settings.

The pinned config is persisted in **local DataStore and never synced** — nav layout is a device-specific UI preference, exactly like the theme (ADR-0014). Paired-only destinations (Couple, Combined view, Partner Debt) use **hide + graceful collapse**: they appear in the picker only when paired, and a pinned-then-unpaired destination is hidden at render time (not deleted from config) so re-pairing restores the user's layout.

**Consequences.** Adding a future module is a one-line registry entry; the bar, the More grid, and the editor all pick it up. State preservation (`saveState`/`restoreState`, `launchSingleTop`) must now work over a *dynamic* destination set rather than a fixed enum, which is the main implementation risk (hence built on Opus). Records' existing top-bar callbacks can remain during migration. **Rejected:** five fully-free slots including a removable More (risks orphaning modules with no overflow access); a permanently home-locked Records slot (less freedom than the 4 free pins the user wanted); syncing the layout (it's a per-device preference, and syncing it would fight two phones with different screen habits).

---

**Addendum (2026-07-03) — fixed pin count: floor now equals ceiling.** The original "1..`MAX_PINS`" range let the bar shrink below three pins, which (a) produced the off-center center-⊕ layout at exactly two pins (audit F7) and (b) required a per-destination `understudyId` to keep a hidden paired-only pin from collapsing the bar — a mechanism the audit flagged as fragile (F8: no guard against a paired-only or unknown understudy). Both are structural symptoms of a variable pin count.

**Amended decision:** the bar always shows **exactly `MAX_PINS` (3)** user pins + the fixed center ⊕ Add + the fixed More = 5 items, never fewer. The floor moves from 1 to 3; the ceiling (`MAX_PINS = 3`, ADR-0026's five-item reasoning) is unchanged.

- **`NavConfig`** invariant becomes "always exactly `MAX_PINS` distinct pinnable ids." `pin()`/`unpin()` are replaced by a single `replace(oldId, newId)` (swap in place, count fixed); `move()` (reorder) is unchanged. `deserialize()` self-heals a legacy config with fewer than three valid ids by padding it via registry-order fallback (Alvin/Patty are active beta users with pre-existing saved configs).
- **`NavDestination.understudyId` is deleted.** The single hand-written "Couple's stand-in is Manage" rule is replaced by one generic mechanism in **`NavResolver.visiblePinIds()`**: a two-pass resolution that keeps every currently-available stored pin in its slot, then back-fills each remaining slot (vacated by a paired-only hide, or missing because the config was short) with the next module in registry order that is pinnable, available, and not already chosen. Manage still ends up back-filling Couple's slot in practice (it's near the top of the registry) — no special case needed. This one code path now covers both "pin hidden by pairing" and "legacy short config," which were previously separate and inconsistent.
- **Editor:** pinned rows lose their ✕ (no bare removal). Tapping a module under "More modules" opens a "Replace which pin?" picker listing the current three pins; choosing one swaps via `NavConfig.replace()`. Drag-to-reorder is unchanged.

This **retroactively closes audit F8** (the understudy mechanism it guarded no longer exists) and removes the two-pin state that F7's formula had to accommodate (the `((visiblePins.size + 1) / 2)` split is still correct and defensive, but at a constant 3 pins it always yields `[P1][P2] ⊕ [P3]`).
