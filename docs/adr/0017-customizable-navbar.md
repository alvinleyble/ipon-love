# Customizable bottom navbar via a destination registry

**Context.** The bottom nav was a fixed five-tab `enum` (`TopLevelDestination`) hard-wired in `IponApp`, with every other module (Notes, Recurring, Couple, Settings, …) reachable only through ad-hoc top-bar callbacks on the Records screen. V1.3 wants users to choose which modules sit in the bar and rearrange them, with an overflow for the rest. A fixed enum can't express a user-defined, runtime-mutable, paired-aware set.

**Decision.** Introduce a **destination registry** — a single list of nav-able destinations, each with `id`, `label`, `icon`, `route`, and `requiresPaired`. The bottom bar is built dynamically from a stored config: **up to 4 user-pinned, reorderable destinations + an always-present "More"** as the last item (min 1 pin; the first pin is the `NavHost` start destination). Default pins: Records, Analysis, Couple, Budgets. "More" opens a modal bottom-sheet grid of all currently-visible modules plus an "Edit navbar" entry (drag-to-reorder / pin / unpin); the editor is also linked from Settings.

The pinned config is persisted in **local DataStore and never synced** — nav layout is a device-specific UI preference, exactly like the theme (ADR-0014). Paired-only destinations (Couple, Combined view, Partner Debt) use **hide + graceful collapse**: they appear in the picker only when paired, and a pinned-then-unpaired destination is hidden at render time (not deleted from config) so re-pairing restores the user's layout.

**Consequences.** Adding a future module is a one-line registry entry; the bar, the More grid, and the editor all pick it up. State preservation (`saveState`/`restoreState`, `launchSingleTop`) must now work over a *dynamic* destination set rather than a fixed enum, which is the main implementation risk (hence built on Opus). Records' existing top-bar callbacks can remain during migration. **Rejected:** five fully-free slots including a removable More (risks orphaning modules with no overflow access); a permanently home-locked Records slot (less freedom than the 4 free pins the user wanted); syncing the layout (it's a per-device preference, and syncing it would fight two phones with different screen habits).
