# Shared accounts & categories are couple-owned; private spend is disallowed on them

**Context.** Until now, partner data was strictly **read-only replication** through redacting views (ADR-0004/0005): you can only write your own rows, and the combined view deliberately omits partner *balances* because private activity makes them uncomputable (ADR-0011). V1.3 wants genuine **shared accounts** (both partners log transactions against one account and see its balance) and a **shared category** set — a write-sharing capability the read-replication model can't express.

**Decision.** Extend the existing couple-owned write primitive (already proven for shared budgets, partner debts, shared notes: `couple_id` set, `user_id` null, an `_couple` RLS policy gated on `auth_couple_id()`) to **accounts and categories**. Add `couple_id` and `created_by` columns to both tables, plus `accounts_couple` / `categories_couple` policies. Couple-owned rows replicate to both partners through the **base-table pull** (the `_couple` select policy returns them), not through a redacting view — redaction is only for partner-*owned* rows.

A shared account's balance must sum **both** partners' transactions against it. To keep that computable, **a transaction logged against a shared account is forced non-private** (`is_private = false`, enforced in `TransactionValidator` and a DB check). This is a principled **carve-out from ADR-0011**: shared accounts *can* show a balance precisely because all their activity is non-private by rule. `AccountBalanceCalculator` sums across both `user_id`s for shared accounts, and the balance shows in both partners' Accounts lists. Shared categories are usable on any transaction and appear in both partners' pickers; **no auto-migration** of existing personal categories (dev phase, no live users — see `dev-phase-no-prod`).

**Lifecycle.** Both **un-share** (voluntary toggle) and **unpair** (the ADR-0008 escape hatch) resolve a couple-owned account/category by **revert-to-creator**: the row becomes the creator's personal row (`user_id = created_by`, `couple_id = null`), keeping its history and balance for the creator; it is purged from the other partner, whose transactions that referenced it fall back to "Unknown account" / "Uncategorized". Unpair therefore stays **unilateral and always-succeeds** — it is never blocked on shared-account state, so a partner can never trap the other in the couple. This **amends ADR-0008**, which previously only soft-deleted shared (forward-looking) budgets.

**Amendment (2026-07-11, v1.6.5 Item 20) — the voluntary un-share toggle is creator-only.** The original wording implied *either* partner could un-share and the row would revert to its creator "regardless of who un-shares." That is unsafe for the **client-side** toggle: the revert sets `user_id = created_by`, so when a *non-creator* un-shares a partner-created row, their device writes a row owned by the **other** partner — which RLS (`accounts_owner`/`accounts_couple`) forbids that device to push. Because a table's dirty rows push as one atomic upsert, that single un-pushable "poison" row fails the whole batch and wedges every pending row, and with it sign-out (ADR-0021, and the concrete incident in `docs/build/v1.6.5.md` Item 20). So the **voluntary toggle is now restricted to the creator** — `unshareAccount`/`unshareCategory` no-op for a non-creator, and the UI hides "Make personal" for them (surfaced as `Account.isCreator`/`Category.isCreator`). This matches the owner-only un-share that savings goals and notes already enforce. **Unpair is unchanged** — it reverts *every* couple row to its respective creator server-side via the `unpair()` RPC (which bypasses RLS), so its either-party, always-succeeds guarantee holds. As defence-in-depth, the flip-model syncers (accounts, categories, budgets) filter any row this session cannot own out of the push (`isLocallyPushable`), so a stray poison row — e.g. from an offline edit during an unpair race — can never again wedge a batch; it stays a benign local orphan until a pull converges it (generalising the `goal_contributions` F1 guard, ADR-0025).

**Consequences.** Real joint accounts work offline and converge under the existing sync/LWW machinery, reusing a primitive the codebase already trusts. The privacy cost is explicit and bounded: you cannot record a *private* transaction on a shared account — if you need privacy, use a personal account. Revert-to-creator preserves the more valuable artifact (an account with balance/history) instead of destroying it, at the cost of a `created_by` column and revert logic in both the toggle and the unpair RPC. Shared writes must also ring the live-sync bell (ADR-0015) so the partner pulls promptly. **Rejected:** owner+write-grant (asymmetric, no clean precedent, gnarlier RLS); allowing private spend on shared accounts then hiding the balance (a shared account with no trustworthy balance is pointless); soft-deleting shared accounts on unpair like budgets (destroys a real account with balance for both partners); blocking unpair/un-share while in use (breaks the unilateral-exit guarantee and would need a bulk-reassign feature to avoid dead-ending users); shared categories with auto-mapping of existing categories (unnecessary pre-launch and a large migration surface).
