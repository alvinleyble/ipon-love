# Partner debt becomes transaction-linked: auto-netting, paid-on-behalf, two-leg settlement

**Context.** The Partner Debt Tracker recorded debts and payments as a standalone ledger. The couple **net** was already derived (`PartnerDebtCalculator` signs each debt's remaining and sums to `I_OWE / OWED_TO_ME / SETTLED`), but the underlying records stayed open independently, so two opposing debts (Patty owes ₱3k, Alvin owes ₱1k) each still "needed" payment even though the real position is ₱2k one way. Debts were also disconnected from money movement: creating one never recorded the expense, and settling one never touched account balances. V1.3 wants debts wired to the transaction ledger.

**Decision.** Three linked changes, all reusing existing primitives:

1. **Auto-netting (#9).** When a debt is created opposite to existing open debt, it immediately offsets (oldest-first / FIFO) via **linked `DebtPayment`s** — a payment that settles the new debt and a matching payment that reduces the existing one, each marked as a netting payment referencing its counter-debt. Nothing is destroyed (fully auditable); deleting a debt removes its netting payments. The offsetting payment IDs must be **deterministic** so that two partners creating opposing debts offline simultaneously converge on the same netting instead of double-netting.

2. **Paid-on-behalf (#12).** A "Paid for Partner" toggle on transaction entry reveals an *amount owed* field defaulting to the full transaction amount (covers both "I paid for your thing" and bill-splitting). On save it records the normal transaction **and** a partner debt (borrower = partner, lender = me, amount = owed), which feeds auto-netting. The debt stores `source_transaction_id` for display only — **fire-and-forget**: editing or deleting the transaction does not cascade to the debt.

3. **Two-leg settlement (#14).** Settling generates real ledger transactions. Because each user may only write their own rows and they are on different devices, the payor records the couple-owned `DebtPayment` (carrying `payor_account_id` + `payor_txn_id`) and their own outflow transaction; the **receiver leg is an inline, optional affordance** on the debt board ("Add to my account") that creates the receiver's inflow transaction and stamps `receiver_txn_id`. If the receiver never acts, the payment is still valid with only the payor's leg (graceful degradation to payor-only). Both legs are ordinary `EXPENSE`/`INCOME` (so balances move correctly) but carry an `is_settlement` flag; **Analysis (donut / expense-flow / calendar) excludes flagged rows** while balance derivation includes them, so a repayment never looks like spending.

**Consequences.** The debt board stops showing contradictory open records, debts reflect real money movement, and settlements respect RLS and offline-first without a notification/inbox surface. New nullable columns (Room + schema): a netting reference + counter-debt on `partner_debt_payments`; `source_transaction_id`, `payor_account_id`, `payor_txn_id`, `receiver_txn_id` across the debt/payment tables; `is_settlement` on `transactions`. The cross-device, multi-ADR money math (built on Opus) carries the real risk — especially the offline double-netting convergence. **Rejected:** keeping records open and relying on the displayed net only (the original confusing state); manual "Reconcile" netting (users forget; the dual-open state lingers); a full push-notification + action-needed inbox for settlements (heavy machinery for V1.3); payor-only settlement with no receiver facilitation (receiver balance never reflects the repayment); modeling legs as plain expense/income with no flag (pollutes spending charts); a new SETTLEMENT transaction type (breaks current TRANSFER assumptions, more plumbing than a boolean).
