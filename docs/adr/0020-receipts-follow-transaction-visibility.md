# Transaction receipts follow the transaction's visibility

**Context.** V1.3 adds a receipt photo per transaction. The data column already exists (`attachment_url` on `transactions`, and on `TransactionEntity` / `TransactionDto` / `PartnerTransactionDto`), but the `partner_transactions` redacting view never selected it, so partners could never see receipts. The question was whether a receipt on a *non-private* transaction (which is already visible to the partner in the combined view) should also expose its receipt image.

**Decision.** Receipts **follow the transaction's visibility**. Add `attachment_url` to the `partner_transactions` view, redacted (nulled) when the row is `is_private` or `is_deleted`, exactly like the other content columns (ADR-0005). Add Storage RLS so couple members can read each other's receipt objects. The combined view renders the partner's receipt for shared transactions. Storage and upload reuse the Slice E pattern: a single receipt per transaction via the existing `attachment_url`, plus a local-only `attachment_local_path` (Room, not synced) for the offline upload-pending state, uploaded by a `ReceiptUploader` `PreSyncStep`.

**Consequences.** A "financially open couple" (the ADR-0011 target user) sees proof of shared spending, consistent with the fact that amount/category/note already share by default. Two bounded caveats, both accepted as consistent with already-shipped behavior: (1) transactions default to **non-private**, so receipts replicate to the partner by default the moment created — privacy requires marking the transaction private; (2) the redacting view can null the *URL*, but a partner who already synced and cached the image keeps it — "going private later" cannot claw back an already-replicated receipt. This is the same residual already accepted for shared note images (Slice E); Storage RLS protects the object for clients that did not already fetch it. **Rejected:** owner-private receipts (asymmetric — the partner sees the transaction but not its proof, and undersells the shared-finance use case).
