# Sign-out wipes local data; a login guard backstops it

**Context.** Room is the offline-first source of truth and a process `@Singleton` ([DatabaseModule](../../app/src/main/java/com/iponlove/app/core/di/DatabaseModule.kt)) that is never recreated across a sign-out — `AuthRepositoryImpl.signOut()` only cleared the Supabase session. So after user A signed out and user B signed in on the same device, B's session read A's rows out of the same Room database. Worse, couple-owned rows leak past even an owner filter: the account/category DAOs select `WHERE (userId = :me OR coupleId IS NOT NULL)` (ADR-0018), so any shared row stays visible regardless of who is signed in. Sync cursors compound it — they are per-account pull positions but were never reset, so even a correct re-pull would be skipped. A beta self-test surfaced this as a cross-account data leak (privacy-critical).

**Decision.** Treat sign-out as a **local-data lifecycle boundary** and wipe everything account-scoped, with a login-time guard as the defensive net for paths that skip a clean sign-out.

- **`LocalDataWiper`** ([core/session](../../app/src/main/java/com/iponlove/app/core/session/LocalDataWiper.kt)) clears three things that are meaningless apart: Room (`IponDatabase.clearAll()` → `clearAllTables()` off the main thread), the sync pull cursors (`SyncCursorStore.reset()` — back to `server_rev = 0` so a re-login re-pulls the full history instead of skipping everything below a stale cursor), and the per-device nav layout (`NavConfigRepository.reset()`). It does **not** touch the Supabase session (the auth layer owns that) nor `LastActiveUserStore` (the guard's own bookkeeping, which must outlive the wipe).
- **On sign-out** ([AuthViewModel](../../app/src/main/java/com/iponlove/app/feature/auth/presentation/AuthViewModel.kt)): cancel the sync worker, **best-effort `pushOnly()`** to flush pending rows so a synced device loses nothing, then sign out of Supabase and wipe — but **only after** a successful sign-out, so a failed sign-out (same user still logged in) never destroys the data they are still looking at.
- **Offline safety.** `BaseTableSyncer.push()` short-circuits to a no-op when nothing is dirty (no network call), so `pushOnly()` *throwing* means precisely "there were pending rows we couldn't send" — i.e. offline with unsynced changes. In that one case we surface a confirm dialog ("Unsynced changes will be erased — sign out anyway?") instead of silently wiping. A no-op push returns normally and wipes safely.
- **Login guard** (`AccountSwitchGuard`, run from [MainActivity](../../app/src/main/java/com/iponlove/app/MainActivity.kt) before the first sync): compares the freshly authenticated id against `LastActiveUserStore`; if a *different* user now holds the device, wipe before syncing. Always records the current user. A first-ever login (no recorded user) never wipes — nothing to leak, Room already empty. This covers the crash-mid-logout, reinstall-with-restored-session, and any-future-account-switch paths that bypass the sign-out wipe.

**Consequences.** The wipe is a privacy boundary, not a sync optimization: a re-login on the same account pays a full re-pull (cursors reset to 0), which is correct — Room is empty, the history must come back. Resetting the nav layout means a different account starts on default pins; theme and the app-lock PIN are deliberately **left** for now (cosmetic, and the PIN is a separate local-security concern — a future ADR may revisit clearing the PIN on account switch). `LastActiveUserStore` lives in its own `session_prefs` DataStore so it survives the wipe. The offline-confirm inference can false-positive if a push fails online for a non-network reason (e.g. an RLS rejection); the dialog wording ("we couldn't sync your latest changes") stays honest in that case, and the user can still choose to stay signed in. **Rejected:** putting the wipe inside `AuthRepositoryImpl` (would couple the thin Supabase adapter to Room + every feature's DataStore) and a domain `SignOutUseCase` that imports Room (violates the zero-Android-imports domain rule) — the wiper is infrastructure in `core/session`, injected into the presentation layer like `AppLockManager`.
