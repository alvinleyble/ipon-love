# Password recovery is a distinct `AuthStatus`, not folded into `Authenticated`

**Context.** supabase-kt's `SessionStatus.Authenticated` fires identically whether the session came from an ordinary sign-in or from tapping a password-recovery email link — `AuthRepositoryImpl.status` mapped it 1:1 to `AuthStatus.Authenticated` regardless of origin. That matters because `MainActivity`'s `Authenticated` branch immediately triggers a heavy cascade (`EnsureCurrentUserRowUseCase`, a full sync, the onboarding decision, WorkManager enqueues, widget update) — none of which should run for a session that exists only to let the user set a new password. Decompiling the installed supabase-kt 3.6.0 `auth-kt` jar confirmed the SDK does carry a distinguishing signal: `UserSession.type`, a `String` parsed straight from the recovery deep link's fragment (`type=recovery`), reachable as `(sessionStatus as SessionStatus.Authenticated).session.type`. It just wasn't being read.

**Decision.** `AuthRepositoryImpl.status` now checks `session.type == "recovery"` and maps it to a new `AuthStatus.PasswordRecovery` state instead of `Authenticated`. `MainActivity` routes this state to a dedicated "set new password" screen, reachable only via the recovery deep link — never the ordinary app shell. On a successful password update, the app forces `client.auth.signOut()` and returns to the normal sign-in screen rather than continuing the recovery session straight into the app. This matches the standard reset-password pattern (Gmail, banking apps) and avoids depending on unverified SDK behavior — whether `session.type` naturally clears after `updateUser()` was never checked, so sign-out sidesteps the question entirely.

**Rejected:** auto-continuing into `Authenticated` after a successful password update. Simpler (no forced re-login) but weaker: it doesn't confirm the new password actually works end-to-end, and correctness would hinge on unverified SDK internals rather than an explicit, controlled transition.
