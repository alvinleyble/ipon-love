# PIN lockout: flat 5-attempt threshold, timed cooldown, DataStore-persisted; biometric OS lockout now surfaced too

**Context.** The app-lock's PIN path had no attempt-limiting at all — grepping the whole `feature/applock/` tree found no counter, lockout, or fail-count field anywhere; `AppLockViewModel.verify()` just set an error message and let the user retry immediately, indefinitely. Biometric already gets OS-level lockout for free (`BiometricPrompt`'s `ERROR_LOCKOUT`/`ERROR_LOCKOUT_PERMANENT`), but the code silently swallowed every error code into a bare, message-less fallback to the PIN pad — discovered while investigating why "Use biometric" appeared to do nothing (Item 6/7, v1.6.1 plan).

**Decision.** PIN gets a flat 5-attempt threshold before a 30-second timed cooldown — not progressive, and not forcing the existing "Forgot PIN" re-auth flow (email+password re-authentication, already built) as the only way out. The failed-attempt counter persists in DataStore, so force-killing the app cannot bypass the lockout, and it resets **only on a successful unlock** — never on elapsed idle time. "Forgot PIN" remains available throughout as an opt-in escape hatch. Biometric's OS-level lockout codes are now surfaced with a message ("Biometric temporarily locked out — use your PIN") instead of a silent fallback.

**Rejected:** progressive backoff (this PIN only gates local access to an already-authenticated session, not a payment — the extra complexity isn't earning its keep); forcing the re-auth flow after N failures (over-punishes an honest typo); an in-memory-only counter (trivially bypassed by killing the app); resetting the counter after elapsed time instead of only on success (lets a brute-forcer simply wait out the window indefinitely).
