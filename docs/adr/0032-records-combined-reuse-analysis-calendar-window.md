# Records/Combined transaction lists adopt a calendar-month window + day-grouped headers, sharing month math with Analysis via core/

**Context.** `TransactionDao.observeTransactions()` and `observeCombined()` are unbounded — no `LIMIT`, no date filter — so Room re-emits the user's *entire* transaction history on every write, and `TransactionsScreen`/`CombinedViewModel` render it as one flat, undifferentiated list forever (v1.6.1 plan, Item 2). Analysis already solved an adjacent problem: `AnalysisPeriodRange.windowFor`/`.step` computes calendar-aligned windows (see ADR-0030, `Analysis period` glossary term) and pages them via `PeriodStepper`.

**Decision.**
1. **Scope:** both the personal Records screen and the couple's Combined view get the fix — they have the same unbounded-growth problem architecturally, just different ViewModels.
2. **Independent per-screen state:** each screen tracks its own viewed month independently. No shared "current month" state between `TransactionsViewModel` and `CombinedViewModel` — switching one doesn't move the other.
3. **Default window:** bounded to the current calendar month (July 1–31, not "last 30 days"), steppable via prev/next arrows — the same calendar-bucket semantics as Analysis's `MONTH` period (ADR-0030), not a trailing window.
4. **Shared math lives in `core/`, not a feature-to-feature import.** The month-snap/step logic (`withDayOfMonth(1)` / `plusMonths(1)`) is extracted into a small `core/date/MonthWindow.kt` utility that both `AnalysisPeriodRange` and the Records/Combined code call — Transactions does not import Analysis's domain package directly. Matches CLAUDE.md's Scalability Principle (shared logic belongs in `core/`, not buried in one feature).
5. **Day-grouped sticky headers, not month-grouped.** Since the view is already bounded to a single month, a month-level header would be redundant with the picker itself. Day headers use relative labels ("Today", "Yesterday") only when the viewed month is the actual current month; every other case (other days in the current month, or any day in a past/future month) gets a plain date format.
6. **Empty state distinguishes "no transactions this month" vs. "no transactions ever."** The existing zero-state ("No transactions yet / Tap + to record...") is reserved for users with genuinely zero transactions across all time; a user with history elsewhere but nothing in the viewed month sees a distinct, non-alarming "No transactions this month" message.
7. **Search/filter bar (account/category/type) is explicitly deferred** to a separate future slice, not bundled into this fix.

**Rejected:** month-grouped headers (redundant once the window is already one month); a single shared "current month" state across Records and Combined (surprising — browsing March in Records shouldn't move Combined off the current month); a single generic empty-state message for both the true-zero and zero-this-month cases (misleading for an existing user who just has no activity in the viewed month); Records importing `AnalysisPeriodRange` directly (couples two features' domain layers together for logic that isn't actually Analysis-specific).
