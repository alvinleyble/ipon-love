# Every top-level module becomes its own nested nav graph, uniformly, so tab switches preserve place and re-tapping resets to root

**Context.** `IponApp.kt`'s `NavHost` is one flat graph — every module root (Records, Analysis, Manage, Couple, Settings, Calculator, Savings) and every sub-screen it can push (Recurring, Profile, SettingsCouple, AppLockSetup, NavEditor, Help, BetaFeedback, UpcomingFeatures, GoalEditor, GoalDetail) are separate top-level `composable()` entries in the same graph. `switchTab()`'s `popUpTo(graph.findStartDestination().id) { saveState = true }` always collapses the back stack down to the app's *one* fixed start route, not "this module's own root" — so leaving a module mid-flow (e.g. Records → Recurring) and returning via another tab lands back on the module's root, discarding the pushed sub-screen, rather than resuming where it was left (v1.6.1 plan, Item 14). Re-tapping the tab you're already inside is also a no-op today, rather than resetting that module to its root. Confirmed by reading the code: only Records (→ Recurring, and Notes until Item 13 promotes it out), Settings (→ Profile, SettingsCouple, AppLockSetup, NavEditor, Help, BetaFeedback, UpcomingFeatures), and Savings (→ GoalEditor, GoalDetail) push real sub-screens via the `NavController` — Manage's and Couple's internal sections are an in-screen `PrimaryTabRow`/`HorizontalPager`, not nav routes, and are unaffected.

**Decision.**
1. **Every pinnable module gets its own nested graph, not just the three that currently have sub-screens.** Analysis, Manage, Couple, and Calculator — which have no sub-screens today — are wrapped in single-node nested graphs too, so `switchTab`/re-tap-to-root logic has exactly one code path regardless of how many screens a module contains. A module that later grows a sub-screen (the way Records did) needs no nav-mechanism changes, only a new `composable()` added inside its existing graph.
2. **Add/Edit Transaction stays a standalone top-level route, outside every module's nested graph.** It's reached both from the global center ⊕ button and from inside Records, so nesting it inside Records' graph would make the ⊕ button's behavior depend on which tab happens to be active. It never inherits Records' reset-on-retap behavior.
3. **Re-tapping the active tab resets only the `NavController` back stack for that module's graph** (pops to the graph's start destination) — it does not reset scroll position, viewed month/period, or any other in-screen state. Keeps this item's scope to navigation, not a redefinition of what "root" means for every screen's internal state.
4. **`NavResolver`/`NavConfig` pin resolution needs no nested-vs-flat branching**, a direct consequence of decision 1 — a pin id always resolves to a graph route, and entering it always means "navigate into this graph, restoring its saved state," whether that graph has one node or five.

**Rejected:** only nesting the three modules that currently push sub-screens (Records/Settings/Savings), leaving Analysis/Manage/Couple/Calculator as flat composable routes — saves some upfront boilerplate, but leaves two parallel navigation mechanisms to maintain and would force this decision to be revisited the next time a currently-flat module grows a sub-screen. Nesting Add/Edit Transaction inside Records — simpler back-stack story for Records specifically, but makes the global ⊕ button's landing behavior inconsistent depending on the active tab. Also resetting scroll/viewed-period state on re-tap — closer to how some bottom-nav apps behave (tap Home again → scrolls to top), but expands this item into a per-screen state-reset design pass rather than a navigation fix.
