# First-run tutorial is a tap-to-advance coach-mark sequence, engine in core/ui/, gated by an independent local flag

**Context.** Alvin wants a guided, interactive tour teaching a new (or freshly-reinstalled) user where features live, replayable on demand from Settings (v1.6.1 plan, Item 15). The existing `OnboardingGraph` (Welcome → pair-or-solo → starter templates, ADR-0024) is a different concern — account/data setup gated on synced-server-state emptiness (`ShouldShowOnboardingUseCase`) — and deliberately skips a returning user whose real data already exists on the server, which is exactly one of the two cases this tutorial must fire for (the other being a genuinely new user). Nothing like a coach-mark/spotlight/tooltip-overlay component exists anywhere in `core/ui/` today (confirmed by a whole-tree grep during Item 10's work). This item depends on Item 14 (ADR-0033)'s nav rework being settled first, since a cross-tab tutorial script needs to know what nav shape it's driving through.

**Decision.**
1. **Independent gate, not a fourth onboarding step.** A new local-only DataStore boolean (`tutorial_seen`), unrelated to `isOnboardingDone`, checked once the app shell mounts (after `OnboardingGraph` completes for a new user, or after a normal login for a returning one). Because it's local-only, it naturally re-arms whenever local storage is cleared — covering both of Alvin's trigger cases (brand-new user, and existing user with wiped local storage) with one mechanism, without special-casing "was this an existing user?"
2. **Step script, V1 scope:** bottom-nav pins, the center ⊕ Add button, the More sheet, and the navbar editor (as a "you can customize these pins" callout). No broader survey of every feature — kept short so testers don't skip it.
3. **Visual style: a simple anchored tooltip** (arrow/callout near the target), not a full dimmed-cutout spotlight. Compose has no built-in spotlight primitive, and a cutout-mask synced to on-screen coordinates through scroll/resize is real extra engineering the tour doesn't need to earn its keep.
4. **Each step advances only when the user taps the real, highlighted target** — not by driving navigation programmatically while the user taps a generic "Next." The tutorial observes nav/sheet state to detect the real action happened; it does not call `NavController.navigate()`/toggle `showMore` itself. Teaches muscle memory instead of playing a slideshow, and avoids coupling the tutorial engine to write-access over whatever nav shape ADR-0033 lands on.
5. **Reusable engine in `core/ui/CoachMark.kt`**: target-highlighting (via `onGloballyPositioned` coordinates), anchored tooltip rendering, and skip/next/done sequencing, with zero Ipon-specific knowledge. The actual step script (which screens, what copy, in what order) lives in a small `feature/tutorial/` module that consumes the engine — per CLAUDE.md's Scalability Principle, the generic primitive doesn't belong buried inside one feature.
6. **Replay entry point:** a "Replay tutorial" `ListItem` in Settings' existing Support section (same section as Help/Beta feedback). Replaying does not touch or reset `tutorial_seen` — it's a separate manual trigger, not a re-arming of the automatic one.

**Rejected:** bolting a fourth step onto `OnboardingGraph` — inherits `ShouldShowOnboardingUseCase`'s synced-state gate, which is designed to *skip* exactly the "existing user, wiped local storage" case Alvin explicitly wants covered. A full dimmed-spotlight visual — more polished, but real extra build cost (cutout-mask math) this app's lean build style doesn't need to pay for a first pass. Auto-driving navigation with the user just tapping "Next" — guarantees a smooth uninterruptible tour, but couples the tutorial engine to write-access over nav state and needs a clean undo path if the user backs out mid-tour; tap-to-advance sidesteps both problems at the cost of needing a sane fallback if the user taps the wrong thing.
