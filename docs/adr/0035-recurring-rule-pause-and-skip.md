# Recurring rules gain pause/resume (jump-forward on resume) and single-occurrence skip, both via the existing per-rule menu

**Context.** `RecurringRule` (`feature/recurring/domain/model/RecurringRule.kt`) has no `isPaused`/`isActive` field — `MaterializeRecurringRulesUseCase` processes every rule unconditionally, and the only way to stop future occurrences is `DeleteRecurringRuleUseCase` (soft-delete, permanent). There's no way to temporarily suspend a rule (e.g. a cancelled-for-now subscription) or skip a single upcoming occurrence (e.g. a one-off missed bill) without deleting the rule outright (v1.6.1 plan, Item 18). `RecurringScreen.kt`'s `RecurringRow` already has a per-row overflow `DropdownMenu` with a "Delete" item — the natural, zero-new-pattern slot for these actions.

**Decision.**
1. **Both capabilities ship together:** pause/resume (indefinite suspension) and single-occurrence skip (one-shot). Skip's date-stepping logic is a strict subset of what pause/resume already needs, so building both together is cheap relative to building either alone.
2. **Pause:** a new `isPaused: Boolean` field on `RecurringRule`. `MaterializeRecurringRulesUseCase` skips any paused rule entirely — no occurrences generate while paused.
3. **Resume jumps `nextDate` forward to the next occurrence from today, never backfilling missed ones.** Matches the "pausing a subscription" mental model — you're not retroactively charged for the paused months. Avoids ever silently materializing a pile of backdated transactions the moment a rule is resumed.
4. **Skip is a separate, lighter action** — no persisted flag. It steps `nextDate` forward by one period (using the existing `RecurringFrequency`/`interval` math) without calling the materialize path for that occurrence. Distinct from pause: skip affects one occurrence only, the rule keeps generating normally afterward.
5. **Both surfaced via the existing overflow `DropdownMenu`** next to "Delete" — "Pause"/"Resume" (label swaps based on current state) and "Skip next," no new UI component.

**Rejected:** resuming exactly on the original schedule and backfilling missed occurrences — technically matches the stored schedule, but risks surprising the user with several sudden backdated transactions the moment they resume, which is worse than the minor "loss" of a jump-forward. A single combined "pause" mechanism covering both cases (treating a skip as a one-period pause) — conflates two different user intents (indefinite suspension vs. a one-off skip) and would need the same jump-forward-on-resume logic anyway, so there's no real simplification from merging them.

**Amendment (ADR-0048, v1.6.6 Item 37).** Skip gained a second job: for a confirm-on-arrival rule (`auto_post = false`, ADR-0048), a pending occurrence is derived, not stored, so there is nothing to "un-generate" — skipping a pending occurrence is implemented as exactly this ADR's cursor-step-forward, now exposed as *dismiss this occurrence* on the Records "To confirm" card, via a new date-aware `SkipPendingOccurrenceUseCase` (it steps past the specific occurrence date shown on the card, not just "whatever `nextDate` currently is," since a confirm rule's cursor can lag behind several pending occurrences at once). The original `SkipNextRecurringOccurrenceUseCase` this ADR introduced is unchanged and still backs the plain rule-list "Skip next" action. Confirming an occurrence deliberately does *not* use this ADR's cursor-step mechanism — see ADR-0048 decision 4 for why confirm leaves the cursor parked instead.
