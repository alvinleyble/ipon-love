# Budgets gain opt-in rollover: symmetric (unused and overspend both carry forward), no floor, chain breaks at a gap month

**Context.** `Budget` (`feature/budgets/domain/model/Budget.kt`) is a flat `(id, categoryId?, amount, yearMonth)` row — each month is a fully independent record with no reference to the previous month's leftover or overspend. `BudgetProgressCalculator` computes progress against that one month's `amount` only. There's no carry-forward concept anywhere in the budgets feature today (v1.6.1 plan, Item 19).

**Decision.**
1. **Symmetric rollover:** unused budget carries forward as extra room next month, and overspending carries forward as a deficit — a real running ledger, not a one-way "unused stays available" perk. Chosen deliberately over the simpler one-way alternative that was recommended during grilling; a genuine running ledger is worth the added complexity of a possible cascading deficit.
2. **No floor on the carried deficit.** A rolled-over deficit is never clamped to ₱0 — capping it would quietly reintroduce one-way behavior by the back door and contradict the "accurate running ledger" property decision 1 chose. The UI must surface an already-negative effective limit clearly (not just as a bare small number) so it reads as a real signal, not a bug.
3. **Opt-in per budget**, via a new `rolloverEnabled: Boolean` field on `Budget` — not a single global toggle. Different categories genuinely want different behavior (rent never rolls over; groceries/discretionary categories make sense to).
4. **A gap month (no budget row at all for that category/month) breaks the rollover chain.** The carry-forward resets to ₱0 at the next month that does have a row; it does not skip through the gap and keep chaining from before it. A month with no row has no defined spent-vs-limit to carry anything from, so treating the chain as broken there is the only well-defined option — skipping the gap without a real spent/limit pair to consult is not a well-defined weaker option.
5. **Computed at read time, not persisted.** The "effective limit" for a given month (`amount + carriedFromPreviousMonth`) is derived by `BudgetProgressCalculator` chaining backward through consecutive `yearMonth` rows for a rollover-enabled budget, rather than stored on the row. Avoids needing to rewrite historical rows whenever the rollover rule itself changes.

**Rejected:** one-way rollover (unused only, overspend doesn't carry) — simpler and avoids any deficit-spiral risk, but was explicitly rejected in favor of an accurate running ledger. A ₱0 floor on carried deficits — caps the worst case, but undermines the entire point of choosing symmetric rollover in the first place. A single global rollover toggle — much simpler, but forces identical behavior onto every budget regardless of category, which doesn't match how real budgets are actually used (some categories should never roll over). Skipping through gap months to keep a chain alive — more "correct" if the user simply forgot to set a budget one month, but needs a defined spent-vs-limit for a month that has neither, which isn't well-defined without inventing additional rules.
