# Recurring rules default to confirm-on-arrival (derived, unstored pending); auto-post becomes opt-in; cursor advances only on skip

## Context

v1.6.6 Item 37, grilled 2026-07-16, shipped in two slices (`98c5436` free core, `9e9db99` premium forecast layer). Recurring income already worked before this item — a rule on an INCOME category materialized an income transaction the same way an expense rule materializes an expense one (`MaterializeRecurringRulesUseCase`). Alvin's actual request ("schedule an upcoming salary, help how Analysis shows the data") turned out not to need a new "salary" entity — it needed two things the engine didn't have: **forward visibility** of money about to arrive, and a guarantee that the app **never silently records a wrong figure** for a rule whose real-world amount can vary occurrence to occurrence (e.g. a salary that isn't always exactly the same number). Both push the recurring engine from unconditional auto-post to a per-rule confirm step, plus a forecast layer built on the same underlying schedule data.

## Decision

1. **New `auto_post: Boolean` field on `recurring_rules`, default `false`.** `false` (confirm-on-arrival) is the default for every new rule — income and bills alike, since Alvin explicitly wanted bills prompted too, not just income. `true` (the old unconditional behavior) is now an opt-in for charges that are genuinely fixed and never need a look. Auto-post isn't removed, only demoted to opt-in; `MaterializeRecurringRulesUseCase` now only processes `auto_post = true` rules, leaving confirm rules parked.

2. **Pending occurrences are derived, never stored — no `status` column on `transactions`.** A confirm rule's `nextDate` cursor parks on its oldest unconfirmed due date; "pending" is computed live as the occurrences between that cursor and today, minus whatever has already been materialized (deterministic `ruleId:date`-derived UUIDs make this idempotent across devices). This is the load-bearing call of the item: because nothing exists until confirmed, balance (ADR-0007), budgets, and every Analysis query stay untouched — a pending occurrence is invisible to them for free. **Rejected:** a `status = pending` column on `transactions`, which would have forced `WHERE status = confirmed` into every balance/budget/Analysis query — wide surface area, easy to miss a call site, easy to get wrong.

3. **Confirming an occurrence materializes it with an optional this-occurrence amount override; the rule template is unchanged.** Tapping a pending prompt opens an inline amount field pre-filled with the rule's amount; account/category/date come from the rule as-is. The override applies to that single materialized transaction only — a permanent raise is a deliberate rule edit, not a side effect of confirming.

4. **Confirm does not advance the cursor; skip does.** The grilled design's original phrasing ("confirm = materialize + advance cursor; skip = advance cursor without creating") was refined during Slice 1's build: since pending is derived by subtracting the *materialized* id set from the cursor..today window (decision 2), leaving the cursor parked on confirm and letting materialization alone drive exclusion makes an out-of-order confirm (e.g. confirming a later occurrence of a rule before an earlier one) safe by construction — no occurrence can be silently dropped. Skip is the only operation that steps the cursor forward, and it is explicitly one occurrence's worth, date-aware, and regression-guarded (`SkipPendingOccurrenceUseCase`, distinct from the plain rule-list `SkipNextRecurringOccurrenceUseCase`, which just steps whatever `nextDate` currently is and remains unchanged for that caller). See the ADR-0035 amendment below — skip now also serves as "dismiss this pending occurrence."

5. **Pileup is one prompt per occurrence, oldest-first, never merged**, with "Confirm all" / "Skip all" bulk actions alongside the individual ones. Because skip advances a single shared cursor, **skip is only offered on a rule's oldest pending occurrence** (confirm has no such restriction, being order-independent by construction per decision 4) — offering skip on a later occurrence while an earlier one is still pending would silently strand the earlier one. A floor auto-skips occurrences older than roughly 3 months so a neglected daily rule can't spawn hundreds of prompts.

6. **Records gets a pinned "To confirm" card (free)** — per-occurrence confirm-with-tweak and skip, plus bulk actions — **and a "Coming up" preview (premium)**, a lean forward window (14 days, capped at 5 rows) covering all non-paused rules regardless of `auto_post`, self-hiding when empty. Locked, it degrades to a count-only upsell teaser that never reveals amounts. Not inline in the chronological day list — a ledger of the past shouldn't scroll into the future.

7. **Analysis gains a projected month-end Net (premium), current in-progress month only.** `projectedNet = actualNet + upcoming income this month − upcoming bills this month`, shown alongside actual Net and clearly forecast-labeled ("assumes no other spending" — it cannot see unplanned spend, and doesn't try to math around that). It replaces the old backward-looking "Last month income" figure when a schedule exists, falling back to it otherwise. The Flow tab's pre-existing pace-based projection was relabeled "At this pace" to disambiguate it from this schedule-based one.

8. **Premium split:** confirm-on-arrival itself (decisions 1–6) is **free** — it's core money-recording, and CLAUDE.md is explicit that recording your own money is never gated. The forecast layer (decisions 6's "Coming up" preview and decision 7's projected Net) is gated behind a new `RECURRING_FORECAST` feature, dormant per the standing paywall build stance (kill-switch OFF).

9. **Fully personal, same as the rest of the recurring feature.** To-confirm prompts, projected Net, and Coming-up are individual-only; the Combined view is untouched (partner income/balances stay redacted per ADR-0004/0011). A household-level forecast would be its own grilled item on the sharing layer, not implied by this one.

10. **A payday/bill due-date push notification was deliberately deferred**, not built here — pending occurrences surface passively via the Records "To confirm" card on next app open. A due-date reminder needs new scheduled-notification infrastructure that cuts against the app's foreground-sync-only philosophy, and was split out to its own backlog item (v1.6.6 Item 40) pending its own grill.

## Consequences

- **ADR-0007 (derived account balance) is reaffirmed, not amended** — pending occurrences are never stored, so nothing changes about how balance is computed.
- **ADR-0035 is amended** (see that file) — "skip" now has two jobs: stepping a rule's schedule forward (its original purpose) and dismissing a specific pending confirm-on-arrival occurrence (this item), both implemented via the cursor.
- No existing balance, budget, or Analysis query needed a `WHERE` clause change — the entire safety property of decision 2 is that pending occurrences are invisible to money math without being excluded explicitly.
- `RecurringRule` gains `autoPost`; Room v25 → v26. No further schema change from the forecast layer (Slice 2 stayed on v26).
- **Rejected alternatives:** a stored pending/status column on transactions (decision 2); backfilling/auto-generating a distinct "salary" entity instead of reusing income-category recurring rules; bundling a due-date push notification into this item instead of deferring it (decision 10).
