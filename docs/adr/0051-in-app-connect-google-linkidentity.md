# In-app "Connect Google account" uses the OAuth-redirect linkIdentity flow, detects outcome by re-reading identities on resume

## Context

v1.7.0 Item 2 (ADR-0050) adds Google Sign-In via **native** Credential Manager — an on-device ID token exchanged through `signInWith(IDToken)`. It deliberately left one case out: connecting Google to an account you are **already signed into**, from Settings, without signing out. ADR-0050's auto-linking gives an *implicit* path (sign out → Continue with Google with the matching Gmail → auto-link by verified email), but that only ever links an **identical** email and forces a sign-out. This item is the *explicit, discoverable, stay-signed-in* path, and its distinguishing capability is linking a Google account whose email may **differ** from the registered one — the one thing auto-linking cannot do.

The grill (2026-07-23, Opus) established the mechanism constraints that shape everything:

- **supabase-kt has no native ID-token link.** Supabase's "link with native OAuth (ID token)" path (`linkIdentityWithIdToken`) exists only for JS/Dart. Kotlin has only `linkIdentity(Google)`, which runs the **OAuth redirect (browser/Custom Tab)** flow — the exact mechanism ADR-0050 rejected *for login*. It is unavoidable here.
- **Manual linking is a beta feature, OFF by default.** It must be enabled in the Supabase dashboard (`GOTRUE_SECURITY_MANUAL_LINKING_ENABLED`). Without it, `linkIdentity` silently fails the completion.
- **`login-callback` is already a shared deep link.** `com.iponlove.app://login-callback` (registered in `AndroidManifest.xml`, config'd in `createIponSupabaseClient`'s `install(Auth)`) already serves password recovery, email confirmation, and email change — discriminated only by the SDK's internal `session.type`, with zero app-level query/path routing. A fourth consumer (the link redirect) landing there raised a collision fear.
- **The redirect flow's feedback is asymmetric.** In supabase-kt the OAuth `linkIdentity(Google)` suspend call returns as soon as it *launches* the browser; the real success/failure lands later, asynchronously, via the deep link. You cannot `try/catch` the outcome at the call site (unlike the native email flow).

## Decision

**In-app Google connection uses `client.auth.linkIdentity(Google)` (OAuth redirect), launched from the existing app context with no Activity plumbing. The link callback re-imports a same-user session through the unchanged `handleDeeplinks` path; the Profile screen detects the outcome by re-reading `currentIdentitiesOrNull()` on resume — success = a Google identity now present, cancel/failure = unchanged. Scope is connect + status only; unlink is deferred.**

Concretely:

1. **Different-email attach is the target (Q1).** The feature exists to link a Google identity (possibly a *different* email) to the already-signed-in account. Same-email convenience is a free side-benefit, not the justification. UI copy therefore says "Connect a Google account," not "so you can log in with Google."

2. **Connect + status, no unlink (Q2).** Read the identity list to show Connected vs. Not-connected; offer Connect only when unlinked. **Unlink is deferred** to a separate later item — it carries its own risk surface (the only-identity lockout guard; Supabase enforces ≥2 identities server-side) and is the natural cut line.

3. **No new deep-link routing; outcome via resume-diff (Q3).** A `linkIdentity` callback returns a normal same-user session with `type != "recovery"`, so `AuthRepositoryImpl.status` routes it to `Authenticated(sameUserId)` — never `PasswordRecovery`. Same user id ⇒ the ADR-0021 account-switch guard sees no switch, no purge. So **no app-level discriminator is added**; the existing `handleDeeplinks` absorbs the callback transparently. The Profile screen learns the result by **re-reading identities on resume** (success = Google now present; cancel = unchanged, silent).

4. **No Activity; reuse+widen the existing resume refresh (Q5).** Unlike ADR-0050's native flow (needs an Activity for Credential Manager), the redirect `linkIdentity` launches its Custom Tab from the registered app context — the repository calls it directly from a suspend function. `AuthRepository` gains `linkGoogleIdentity()` (fire-and-launch) and `linkedGoogleIdentity(): LinkedIdentity?` (reads `currentIdentitiesOrNull()`, finds `provider == "google"`, returns `{ email }` or null), each behind a UseCase (UseCases own data access). `ProfileViewModel`'s existing per-resume `refreshEmail()` — which already calls `RefreshSessionUseCase` (`retrieveUserForCurrentSession(updateSession = true)`) — is **widened** to also read the linked identity from the freshly-pulled session. The post-link freshness problem is thus solved for free: the session refresh already pulls the post-link user, so identities are current, and success-vs-cancel falls out of the diff.

5. **Silent on cancel *and* completion-failure; typed only on launch failure (Q6).** The redirect splits failures into launch-time (thrown synchronously from `linkIdentity` — no browser, config error) and completion-time (browser opens, Google succeeds, Supabase rejects the link → error redirected back). Completion failures — **the Google account is already linked to a different Ipon account**, or **manual linking is disabled** — arrive only in `handleDeeplinks`'s error callback (currently just logged), *not* at the call site, and via the resume-diff they are **indistinguishable from a user cancel** (identities unchanged either way). Rather than build the first app-level deep-link *result* routing to disambiguate them, both degrade to a **silent no-op plus a neutral "Google account wasn't connected." resume message** (not an alarming error). This is safe because manual-linking-disabled is a config prerequisite we control (won't occur once set) and already-linked-elsewhere is rare and non-destructive. Launch-time failures get a typed `AuthError.GOOGLE_LINK_FAILED`. Routing the real completion error through to a specific message ("already connected to another account") is a noted **fast-follow** if on-device testing shows the silent case is confusing.

6. **Always-show, state-driven row; show the linked Gmail (Q4/Q9).** The row lives under the **Account** section of `ProfileScreen`, grouped with Change password / Change email (above the error-colored Reset/Delete block). Not-linked → a plain full-width `OutlinedButton` "Connect Google account" (matching the sibling buttons; **no Google "G" mark** — consistency within the section beats brand recognition for an in-app settings action). Linked → a read-only row showing "Google account" + the connected Gmail + a Connected affordance. A Google-signup user naturally renders as the linked state. **No "set a password" affordance** for a Google-only user — that inverse feature (`updateUser { password }`) is genuinely out of scope.

7. **Config-only coupling to Item 2; manual-linking is Item 13's own prerequisite (Q7).** The redirect flow needs the Supabase Google provider enabled + Web client + `login-callback` in the redirect allowlist — all *config* artifacts of ADR-0050, none of its *code* (no native `GoogleCredentialClient`, no SHA-1 Android-client registration — those serve native ID-token validation the redirect flow doesn't use). So Item 13 has **no compile-time dependency** on Item 2's code; it is built *after* Item 2 only to inherit that dashboard setup. Item 13's own new external prerequisite: **enable Manual Linking** (the beta flag) in the dashboard — a forgotten flag makes every link silently no-op. Staging-only (prod Supabase doesn't exist yet).

## Consequences

The feature is a thin Settings surface onto `linkIdentity` + an identity read: no schema, Room, or sync change. It coexists with ADR-0050's native login button using a *different* Supabase mechanism (redirect vs. native ID token) — the two are independent calls on `AuthRepository`. The redirect's feedback asymmetry is absorbed by piggybacking the existing per-resume session refresh rather than inventing new deep-link plumbing, at the cost of collapsing rare completion failures into a silent no-op (mitigated by a neutral message, with a routed-error fast-follow on standby). Most of the flow (browser launch, Custom Tab, deep-link return) is Android-heavy → verify-by-running per the testing policy; the JVM-testable seams are the identity-resolution mapper (identity list → `LinkedIdentity?`) and the launch-error → `AuthError` mapping.

**Explicitly out of this decision:** unlinking a Google identity (needs the ≥2-identity guard and a "don't strip your only login" safeguard); adding an email/password identity to a Google-only account (`updateUser { password }`); and routing the specific completion-failure error through to the UI (the Q6 fast-follow).

## Rejected alternatives (summary)

- **Native ID-token linking** (`linkIdentityWithIdToken`, reusing ADR-0050's Credential Manager token) — not offered by supabase-kt for Kotlin; JS/Dart only.
- **An app-level deep-link discriminator** for the link callback — unnecessary: a link callback carries no `recovery` type and no account-switch, so the existing `handleDeeplinks` path routes it correctly with zero new code.
- **Routing the completion error to the ViewModel now** (option b) — introduces the first app-level deep-link *result* routing plus attempt-correlation, to distinguish a rare, non-destructive failure from a cancel; deferred to a fast-follow gated on real-world confusion.
- **Folding this into Item 2** — mixes native + redirect mechanisms and a Settings surface into one item; kept split (this ADR).
- **Including unlink now** — separable, lower-value, own risk surface; deferred.
