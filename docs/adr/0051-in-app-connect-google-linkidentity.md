# In-app "Connect Google account" uses native ID-token linking (Credential Manager), synchronous outcome

> **⚠️ Build-time correction (2026-07-24).** This ADR was grilled + written 2026-07-23 on the premise that **supabase-kt has no native ID-token link in Kotlin** (finding #1 below), which forced the OAuth-**redirect** flow and everything that fell out of it (async deep-link callback, detect-by-resume-diff, silent-on-failure). During the build, disassembling `auth-kt` **3.6.0** (the version in `libs.versions.toml`) showed that premise is **false for this version**: `Auth.linkIdentityWithIdToken(provider, idToken) { nonce = … }` exists, is a real network implementation, and sets the server-side `IDToken.Config.linkIdentity = true` flag (it *links*, it does not sign in as a new user). Alvin chose (2026-07-24) to **pivot to the native ID-token path** — reusing Item 2's Credential Manager `GoogleCredentialClient`. The heading, finding #1, and decisions 3/4/5 are amended below; the rest of the grill (surface, Q1 target, no-unlink, config prereqs) is unchanged. The old redirect design is retained struck-through as the documented fallback if GoTrue rejects ID-token linking on-device.

## Context

v1.7.0 Item 2 (ADR-0050) adds Google Sign-In via **native** Credential Manager — an on-device ID token exchanged through `signInWith(IDToken)`. It deliberately left one case out: connecting Google to an account you are **already signed into**, from Settings, without signing out. ADR-0050's auto-linking gives an *implicit* path (sign out → Continue with Google with the matching Gmail → auto-link by verified email), but that only ever links an **identical** email and forces a sign-out. This item is the *explicit, discoverable, stay-signed-in* path, and its distinguishing capability is linking a Google account whose email may **differ** from the registered one — the one thing auto-linking cannot do.

The grill (2026-07-23, Opus) established the mechanism constraints that shape everything:

- ~~**supabase-kt has no native ID-token link.** Supabase's "link with native OAuth (ID token)" path (`linkIdentityWithIdToken`) exists only for JS/Dart. Kotlin has only `linkIdentity(Google)`, which runs the **OAuth redirect (browser/Custom Tab)** flow — the exact mechanism ADR-0050 rejected *for login*. It is unavoidable here.~~ **CORRECTED 2026-07-24:** this is false for auth-kt **3.6.0**. `Auth.linkIdentityWithIdToken(provider: IDTokenProvider, idToken: String, config: IDToken.Config.() -> Unit)` is present and implemented on Android — it builds an `IDToken.Config` with `linkIdentity = true` and posts to `token?grant_type=id_token` with the current session's authorization, linking the identity to the signed-in user (not creating a new session). So the **native ID-token link path is available**, reusing ADR-0050's on-device Credential Manager token. The OAuth-redirect `linkIdentity(Google)` remains the fallback only if the GoTrue server rejects ID-token-based manual linking at runtime.
- **Manual linking is a beta feature, OFF by default.** It must be enabled in the Supabase dashboard (`GOTRUE_SECURITY_MANUAL_LINKING_ENABLED`). Without it, `linkIdentity` silently fails the completion.
- **`login-callback` is already a shared deep link.** `com.iponlove.app://login-callback` (registered in `AndroidManifest.xml`, config'd in `createIponSupabaseClient`'s `install(Auth)`) already serves password recovery, email confirmation, and email change — discriminated only by the SDK's internal `session.type`, with zero app-level query/path routing. A fourth consumer (the link redirect) landing there raised a collision fear.
- **The redirect flow's feedback is asymmetric.** In supabase-kt the OAuth `linkIdentity(Google)` suspend call returns as soon as it *launches* the browser; the real success/failure lands later, asynchronously, via the deep link. You cannot `try/catch` the outcome at the call site (unlike the native email flow).

## Decision

**(Amended 2026-07-24 — native ID-token path.)** In-app Google connection reuses ADR-0050's Credential Manager `GoogleCredentialClient` to obtain an on-device Google ID token, then calls **`client.auth.linkIdentityWithIdToken(Google, idToken) { nonce = rawNonce }`** — a normal suspend call whose success/failure is **synchronous at the call site** (no browser, no deep link, no resume-diff). `ProfileViewModel.connectGoogle(activity)` runs the same ViewModel→(client)→Repository spine as Item 2's `signInWithGoogle`, flips the row to Connected on success, and surfaces typed errors — including *"already connected to another account"* (`GOOGLE_ALREADY_LINKED`), the specific message the old redirect design could only defer as a fast-follow. The Profile screen still re-reads `currentIdentitiesOrNull()` on resume to render a Google-signup / linked-elsewhere user as Connected. Scope is connect + status only; unlink is deferred.

~~**[Superseded — redirect design, kept as fallback]** In-app Google connection uses `client.auth.linkIdentity(Google)` (OAuth redirect), launched from the existing app context with no Activity plumbing. The link callback re-imports a same-user session through the unchanged `handleDeeplinks` path; the Profile screen detects the outcome by re-reading `currentIdentitiesOrNull()` on resume — success = a Google identity now present, cancel/failure = unchanged. Scope is connect + status only; unlink is deferred.~~

Concretely:

1. **Different-email attach is the target (Q1).** The feature exists to link a Google identity (possibly a *different* email) to the already-signed-in account. Same-email convenience is a free side-benefit, not the justification. UI copy therefore says "Connect a Google account," not "so you can log in with Google."

2. **Connect + status, no unlink (Q2).** Read the identity list to show Connected vs. Not-connected; offer Connect only when unlinked. **Unlink is deferred** to a separate later item — it carries its own risk surface (the only-identity lockout guard; Supabase enforces ≥2 identities server-side) and is the natural cut line.

3. **Native Credential Manager token, synchronous outcome (Q3, amended 2026-07-24).** `connectGoogle(activity)` calls `GoogleCredentialClient.getIdToken(activity, GOOGLE_WEB_CLIENT_ID)` (the same button-flow chooser as Item 2), then `linkGoogleIdentity(idToken, nonce)`. The link succeeds or throws **at the call site** — no browser, no `login-callback` redirect, no `handleDeeplinks` involvement, no resume-diff needed to detect the connect outcome. The Q3 collision fear (a fourth `login-callback` consumer) is moot: the native flow never touches the deep link. ~~*(Was: a `linkIdentity` callback returns a same-user session with `type != "recovery"`, routed to `Authenticated(sameUserId)` via the unchanged `handleDeeplinks`; the screen learns the result by re-reading identities on resume.)*~~ The resume re-read (decision 4) is retained only to render a **Google-signup or linked-elsewhere** user as Connected on entry — not to detect this session's connect.

4. **Reuse the Credential Manager spine; widen the resume refresh for display only (Q5, amended 2026-07-24).** Like ADR-0050's native login, `connectGoogle` takes an **Activity** (Credential Manager needs a UI context) and drives `GoogleCredentialClient` directly from the ViewModel (the deliberate ADR-0050 decision-2 exception to "no data in presentation" — the Activity can't cross a UseCase). `AuthRepository` gains `linkGoogleIdentity(idToken, nonce)` (`linkIdentityWithIdToken(Google, idToken){ nonce = … }`, throws on failure) and `linkedGoogleIdentity(): LinkedIdentity?` (reads `currentIdentitiesOrNull()`, finds `provider == "google"`, returns `{ email }` or null), each behind a UseCase. On connect success the row flips **from the synchronous return** (best-effort email filled from a post-link `linkedGoogleIdentity()` read). `ProfileViewModel`'s per-resume account refresh is still **widened** to read the linked identity so a Google-signup user renders Connected without acting. ~~*(Was: the redirect launches its Custom Tab from app context, no Activity; success detected purely via the widened resume refresh.)*~~

5. **Typed errors at the call site; cancel is silent (Q6, amended 2026-07-24).** Because the link is synchronous, the two completion failures the redirect design had to collapse are now **distinguishable and surfaced directly**: **already linked to another account** → `AuthError.GOOGLE_ALREADY_LINKED` (specific copy — the noted fast-follow, now free), **anything else** (incl. the config-only "manual linking disabled" case we control) → `AuthError.GOOGLE_LINK_FAILED`, network substrings → `AuthError.NETWORK`, classified by a pure `GoogleLinkErrorMapper`. The Credential Manager stage reuses ADR-0050's `GoogleSignInErrorMapper` unchanged (dismissed picker → silent; no account on device → `GOOGLE_NO_ACCOUNT`). ~~*(Was: completion failures arrive only in `handleDeeplinks`'s error callback, indistinguishable from a cancel via the resume-diff, so both degrade to a silent no-op + neutral "Google account wasn't connected." message; routing the specific error was a fast-follow.)*~~

6. **Always-show, state-driven row; show the linked Gmail (Q4/Q9).** The row lives under the **Account** section of `ProfileScreen`, grouped with Change password / Change email (above the error-colored Reset/Delete block). Not-linked → a plain full-width `OutlinedButton` "Connect Google account" (matching the sibling buttons; **no Google "G" mark** — consistency within the section beats brand recognition for an in-app settings action). Linked → a read-only row showing "Google account" + the connected Gmail + a Connected affordance. A Google-signup user naturally renders as the linked state. **No "set a password" affordance** for a Google-only user — that inverse feature (`updateUser { password }`) is genuinely out of scope.

7. **Config-only coupling to Item 2; manual-linking is Item 13's own prerequisite (Q7).** The redirect flow needs the Supabase Google provider enabled + Web client + `login-callback` in the redirect allowlist — all *config* artifacts of ADR-0050, none of its *code* (no native `GoogleCredentialClient`, no SHA-1 Android-client registration — those serve native ID-token validation the redirect flow doesn't use). So Item 13 has **no compile-time dependency** on Item 2's code; it is built *after* Item 2 only to inherit that dashboard setup. Item 13's own new external prerequisite: **enable Manual Linking** (the beta flag) in the dashboard — a forgotten flag makes every link silently no-op. Staging-only (prod Supabase doesn't exist yet).

## Consequences

The feature is a thin Settings surface onto `linkIdentityWithIdToken` + an identity read: no schema, Room, or sync change. It **shares ADR-0050's native mechanism** (Credential Manager → ID token), differing only in the terminal call (`linkIdentityWithIdToken` with `linkIdentity = true` vs. `signInWith(IDToken)`) — the two are independent methods on `AuthRepository` reusing one `GoogleCredentialClient`. Because the outcome is synchronous, there is **no deep-link plumbing and no silent-failure collapse**: errors are typed and shown at the call site. The Credential Manager sheet and the live server exchange are Android/network-heavy → verify-by-running per the testing policy; the JVM-testable seams are the identity-resolution mapper (identity list → `LinkedIdentity?`) and the link-failure → `AuthError` mapping (`GoogleLinkErrorMapper`). **Residual runtime risk:** if the GoTrue server rejects ID-token-based manual linking on-device, fall back to the struck-through OAuth-redirect design above (same manual-linking beta flag prerequisite, which is already enabled).

**Explicitly out of this decision:** unlinking a Google identity (needs the ≥2-identity guard and a "don't strip your only login" safeguard); adding an email/password identity to a Google-only account (`updateUser { password }`); and routing the specific completion-failure error through to the UI (the Q6 fast-follow).

## Rejected alternatives (summary)

- ~~**Native ID-token linking** (`linkIdentityWithIdToken`, reusing ADR-0050's Credential Manager token) — not offered by supabase-kt for Kotlin; JS/Dart only.~~ **This was the mistaken premise — it *is* offered in auth-kt 3.6.0, and is now the chosen path (see the 2026-07-24 build-time correction at the top).** The OAuth-redirect flow is the rejected/fallback alternative instead.
- **An app-level deep-link discriminator** for the link callback — unnecessary: a link callback carries no `recovery` type and no account-switch, so the existing `handleDeeplinks` path routes it correctly with zero new code.
- **Routing the completion error to the ViewModel now** (option b) — introduces the first app-level deep-link *result* routing plus attempt-correlation, to distinguish a rare, non-destructive failure from a cancel; deferred to a fast-follow gated on real-world confusion.
- **Folding this into Item 2** — mixes native + redirect mechanisms and a Settings surface into one item; kept split (this ADR).
- **Including unlink now** — separable, lower-value, own risk surface; deferred.
