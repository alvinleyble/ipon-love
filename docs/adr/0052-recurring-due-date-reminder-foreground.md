# Recurring due-date reminders ride the foreground reactive-notification pattern; off-app alarm scheduling is deliberately declined

> **Amended by [ADR-0056](0056-off-app-recurring-reminder-periodic-sweep.md)** (v1.7.1 Item 12, 2026-07-28). Off-app reach now exists as an **opt-in** `PeriodicWorkRequest` sweep, default OFF — so the third Consequence below ("off-app reach is explicitly out of scope") is superseded. **Decision 1's rejection of `AlarmManager` stands unchanged and is reaffirmed on stronger grounds** in ADR-0056 decision 1; do not read the amendment as licence to revisit it. **Correction:** this ADR's Context claims off-app scheduling "cuts against ADR-0012's foreground-only posture" — that was overstated. [ADR-0012](0012-interactive-in-process-background-workmanager.md)'s decision text explicitly assigns WorkManager "any periodic sweep"; what it forbids is routing *interactive* work through WorkManager. A periodic worker was never evaluated here — only `AlarmManager` was.

## Context

v1.7.1 Item 1, grilled 2026-07-25. Resolves the deferral recorded in [ADR-0048](0048-confirm-on-arrival-recurring.md) decision 10 and split out as [deferred.md Item 40](../build/deferred.md) — a due-date reminder notification for recurring rules, so a user is nudged to confirm a pending occurrence rather than only discovering it passively on the Records "To confirm" card.

The load-bearing tension is with [ADR-0012](0012-interactive-in-process-background-workmanager.md): the app's whole sync/background posture is deliberately foreground-only (interactive sync runs in-process; WorkManager owns background retry/reconnect only). The same philosophy declined periodic background sync for the balance widget (v1.6.6 Item 36) and rejected a battery-optimization exemption (v1.6.6 Item 38, reverted). A due-date reminder is the first feature that could plausibly justify a real OS clock alarm — firing at a fixed hour on the due date even when the app is never opened.

Two facts drove the decision. **(1)** The only reason a scheduled alarm beats the existing passive card is *off-app reach*. **(2)** On the hostile OEM ROMs this app already fights (Alvin's own Transsion/MTK device force-stops the app above Doze — memory `rom-force-stop-nav-reset`), a *force-stopped* app receives no alarms **and** no workers until it is next manually opened. So the heavy path (`AlarmManager` while-idle, `RECEIVE_BOOT_COMPLETED` reschedule, reschedule-on-every-rule-change, Play-policy caution around exact alarms on targetSdk 36) would buy a delivery guarantee that is shakiest exactly where it matters, at meaningful architectural cost and against ADR-0012.

## Decision

1. **Reminders fire on app-open / sync, not on a scheduled clock alarm.** A new `RecurringReminderWorker` mirrors `BudgetAlertWorker` and is enqueued at the same two sites (`MainActivity` post-sync, `SyncWorker` post-sync). No `AlarmManager`, no `RECEIVE_BOOT_COMPLETED`, no new background scheduling. **Rejected:** `AlarmManager.setAndAllowWhileIdle` off-app scheduling — the off-app reach it buys is best-effort on force-stop ROMs and cuts against ADR-0012's foreground-only posture; exact alarms are additionally Play-policy-restricted for a non-alarm app on targetSdk 36.

2. **Scope is confirm-on-arrival rules only** (`auto_post = false`, ADR-0048 decision 1). Auto-post rules record silently and have nothing to confirm, so the "Confirm it now to record!" copy does not apply to them. This scope falls out of reusing `ObservePendingConfirmationsUseCase` wholesale — which already enumerates due-and-unconfirmed occurrences within a ~3-month floor window (ADR-0048 decision 5) and excludes paused rules and already-materialized occurrences. Paused-rule and confirmed-occurrence suppression are therefore free, not new code.

3. **Catch-up, fire once per occurrence.** The reminder fires the first time the app opens on or after an occurrence's due date, for any occurrence still pending — not strictly on the calendar due date. Combined with the app-open trigger of decision 1, a strict same-day rule would fire almost never (miss opening the app that day → no reminder ever). It never fires *before* the due date (no advance warning, per the request). Each occurrence fires exactly once, tracked by a local `RecurringReminderStore` keyed on the deterministic `occurrenceId` (mirrors `BudgetAlertStore`). On first enable the store is seeded with all currently-pending occurrences *without* firing, so enabling the feature (or shipping it, default ON) does not dump the existing backlog — the same guard `BudgetAlertWorker` uses.

4. **One combined toggle, default ON.** A single "Recurring reminders" DataStore boolean (new key alongside `budget_alerts_enabled`), defaulting `true` to match `budgetAlertsEnabled`. The notification copy branches income vs expense internally ("Did your [category] arrive?" / "Have you paid for your [category]?") but is not split into two switches. It ships as one flat row on the Notifications screen; sectioning is deferred to v1.7.1 Items 2-4.

5. **One notification per occurrence, bundled under an Android group.** Each pending occurrence fires its own notification (preserving the per-category personalized copy) with a shared `setGroup` key, so a payday-cluster (salary + several bills due the same day) collapses into one tray stack instead of N loose notifications. A dedicated "Recurring reminders" notification channel (distinct from "Budget Alerts") lets users control it independently in system settings.

6. **Tapping deep-links to the confirm surface** — the Records "To confirm" card (or the Recurring module once v1.7.1 Item 8 promotes it) — reusing the balance widget's existing deep-link plumbing (`pendingWidgetRoute` in `MainActivity`), so the "confirm it now" call to action actually delivers the user to the confirm action.

7. **Fully personal; no schema or Room change.** Recurring rules are owner-only and reminders are per-device/personal, so there is no couples-governance question (contrast the shared-state features governed by ADR-0004/0005/0011). The feature adds only a DataStore preference and a local reminder store — no synced column, no Room migration, no change to ADR-0009's push/pull order.

## Consequences

- **ADR-0012 is reaffirmed, not amended.** Recurring reminders are an extension of the existing reactive-notification pattern (`BudgetAlertWorker`/`BudgetAlertNotifier`), which already only fires on foreground/sync opportunities — not a new background-execution capability. A future agent should not "helpfully" add `AlarmManager` scheduling here; that path was considered and declined (decision 1).
- **[ADR-0048](0048-confirm-on-arrival-recurring.md) decision 10 is resolved.** The deferred payday/bill due-date push is now built, on the foreground pattern rather than the new scheduled infra decision 10 anticipated.
- **Off-app reach is explicitly out of scope.** A user who never opens the app on or after a due date is not nudged by this feature — the passive "To confirm" card (ADR-0048 decision 6) remains the catch-all. If tester feedback shows off-app reach is genuinely missed, a real alarm can be added later as its own grilled item, born aware of the force-stop-ROM caveat above.
- **Rejected alternatives:** off-app `AlarmManager` scheduling (decision 1); strict same-day-only firing (decision 3); splitting income/expense into two toggles (decision 4); a single combined summary notification that would lose per-category copy (decision 5); reminders for auto-post rules (decision 2).
