# Notification inbox as the synced source of truth (bell is primary, OS push is secondary)

**Status:** accepted (2026-07-25, grilled) — constrains [ADR-0052](0052-recurring-due-date-reminder-foreground.md), which is amended by consequence (see below).

## Context

Before this, the app's only notification surface was `BudgetAlertNotifier`: a fire-and-forget OS system-tray push, deduped by a local `BudgetAlertStore` DataStore key set. Swiping a push away lost it forever — no in-app history, no unread state, no record. v1.7.1 grows several notification sources (budget alerts, recurring due-date reminders, per-budget/threshold alerts, partner-debt alerts), and Alvin wanted a real notification bell + browsable history. A web app is imminent (Alvin: possibly starting the following week), making this a genuine multi-client concern, not a single-phone one.

## Decision

Build a **Notification inbox**: a per-user, cloud-synced list that is the **source of truth** for every notification the app raises. The bell (a per-screen top-right icon with an unread badge) opens it. An OS system-tray push is a **secondary, best-effort courtesy** layered on top ("Way A" — inbox-primary, push-secondary).

Concretely:

1. **Inbox-primary delivery.** Every source writes an inbox row first; the OS push is optional and best-effort. This is chosen deliberately over push-primary because the app's own infrastructure makes off-app push unreliable — sync is foreground/reconnect-only (ADR-0012) and the target device force-stops the app above Doze (memory `rom-force-stop-nav-reset`), so a push frequently never fires. Making the inbox authoritative means those notifications simply *wait in the bell* rather than being lost.

2. **Synced, own-user-only entity.** A new synced Room table (Room **v30**) + Supabase table, following the standard push/pull sync rules as a **leaf depending only on the users row** — it sits at the *end* of the ADR-0009 order, has **no partner variant**, and is never replicated (RLS own-row only). The Item 9 "partner logged a debt" notification lands in the *recipient's own* inbox as their own row, generated by their own client from the synced debt — the partner never sees it.

3. **Deterministic identity, create-if-absent generation.** Each category defines a deterministic id (`budget:{id}:{month}:{threshold}`, `recurring:{occurrenceId}`, `debt:{debtId}`) used as the primary key, so the same event produced independently on two clients (phone + web) **merges** into one row instead of duplicating. Generation is *create-if-absent* — re-detecting an already-recorded event must **never** overwrite its read/dismissed state. The inbox row's existence becomes the dedup record, retiring the separate `BudgetAlertStore`.

4. **60-day retention by genuine deletion, not tombstone.** Rows older than 60 days are *hard-deleted*, a narrow, sanctioned exception to the tombstone-only rule (ADR-0010). It is resurrection-safe because "older than 60 days" is computed identically on every client — same spirit as the existing "clear the budget-alert memory at month rollover." User-initiated dismiss/clear-all, by contrast, is an ordinary soft-delete that syncs.

5. **One switch per category** in Settings → Notifications. Off = the category is silent everywhere (no inbox row, no push). Push is best-effort when on; the bell catches OS-dropped pushes for on categories. (Rejected: a two-level "collect in bell" / "also buzz phone" split per category — real but doubles every settings row for a nuance most users never touch; can be added later.)

## Considered options

- **Push-primary, inbox-as-mirror** (bell just logs whatever got pushed) — rejected: an OS-dropped push would leave *no* inbox row, so notifications would still be lost exactly when the OS kills the app, which is the whole failure this is meant to fix.
- **Local-only, per-device inbox** — rejected once the web app became imminent: cross-client read state would diverge on two co-primary devices (laptop + phone), and building it local-only would force a later rewrite. Building synced now mirrors the paywall's "build the infra when the consumer is actually coming" posture.
- **Fully synced but server-generated** (an edge function emits events, all clients read one list) — the "correct" long-term multi-client design, but a large backend lift; deferred to the web-app build. Deterministic client-side ids + create-if-absent give most of its dedup benefit without the backend.

## Consequences

- **Item 1 (ADR-0052) is re-sequenced *after* Item 6 and amended:** the recurring due-date reminder writes an inbox row (best-effort push on top) instead of owning a standalone `RecurringReminderNotifier` + store — a net simplification of Item 1. Its trigger sites, confirm-on-arrival scope, catch-up-once semantics, and copy are unchanged.
- **Item 6 ships with budget alerts migrated in** as the pilot source (proving Way A end-to-end); Items 2-4 and 9 wire into the same inbox as they are built.
- **Item 9's grill inherits a pre-answered delivery half** — it just writes a `debt:{id}` row; that grill only needs copy + settings-section placement.
- Deep-linking to a *specific* sub-item (a single budget, the To-confirm card) with graceful fallback to the parent screen when the source is gone requires lightly extending the current module-root-only deep-link plumbing.
