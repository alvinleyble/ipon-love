# Debt-overpay cascade is a guided multi-debt allocation, filled in tick order, committed atomically

## Context

v1.7.1 Item 10, grilled 2026-07-25. Today settling a partner debt blocks any amount larger than that one row's remaining — a **UI-layer guard** (`PartnerDebtViewModel.saveSettle()` rejects `amount > editor.remaining`), not a domain rule: `RecordDebtPaymentUseCase` already tolerates overpayment (the calculator floors `remaining` at zero), and its own doc comment says so. Alvin wants to lift that block so a single lump payment can spill past one debt into others.

The framing that reshaped the feature came out of the grill's first question. Auto-netting ([ADR-0019](0019-partner-debt-tracker.md), `DebtNettingCalculator`/`ApplyDebtNettingUseCase`) runs at debt **creation**, FIFO-offsetting *opposing-direction* debts down to zero via linked `isNetting` payments. So by settlement time the debts that still have `remaining > 0` are — in the normal case — **all in one direction** (the direction you owe), and their remainings **sum to exactly the couple's net** (`PartnerDebtCalculator.net`). That means "overpay one debt and cascade the excess" is really **"distribute one lump payment across my same-direction debts, capped at what I actually owe."** The overpay gesture is just the entry point; the real operation is a bounded allocation.

A second grill realization: because each debt floors at zero and the net is unchanged regardless of which same-direction debt absorbs what, the money-math end-state is **identical** no matter how the lump is spread. The *only* thing the user's choice controls is **which labeled debt gets marked paid off** (clear "rent", leave "dinner" open). Picking is record-keeping, not math.

## Decision

1. **Same-direction only; the ceiling is automatic.** Overflow flows exclusively to debts where the settling user is the **borrower** ("I owe"). It never crosses into an opposing "they owe me" debt (which would perversely flip who owes whom). Because auto-netting has already zeroed opposing debts, "sum of same-direction remaining" equals the couple's net, so "capped at net debt" needs no separate computation — it falls out of same-direction restriction. **Rejected:** allowing overflow to net against opposing debts (decision would let an "overpayment" reverse the debt direction — never intended).

2. **One screen, progressive disclosure.** Entry is unchanged: tap a debt, pay it. The multi-debt list appears **only when the typed amount exceeds the tapped debt's remaining**. Then the user's other "I owe" debts render **unticked**; ticking a debt makes it eligible to absorb overflow. A normal single-debt payment is byte-for-byte the same experience as today. **Rejected:** always showing the full allocation list (adds noise to the 99% single-payment case); a step-by-step chain dialog ("pay one → where does the excess go? → pick → repeat", Alvin's original phrasing) — more taps, risk of getting stuck mid-chain, same result.

3. **Tick to include; money fills in tick order.** Control granularity is a checkbox per debt (not per-debt amount typing, not drag-to-reorder). The lump fills the ticked debts **in the order they were ticked** — first ticked is paid first, each floored at its own remaining, the last-touched debt taking the remainder (possibly partial). Tick order is what delivers the "choose which debt is left open" goal with zero extra UI. **Rejected:** always-oldest-first fill (can't express "clear the newer debt, leave the older one open"); per-debt amount entry (fiddly, largest money-math test surface for no added real capability).

4. **Ceiling = sum of ticked debts' remaining, live-updating.** The tapped debt is always ticked. The maximum payable is the total remaining of the currently-ticked debts, and it rises as more are ticked. Typing more than that is **blocked** with a clear message ("Select more debts to cover ₱X — currently you can pay up to ₱Y"), never silently capped, never allowed to overshoot. A "Pay full ₱N" shortcut (tick-all + fill) is a nicety.

5. **One EXPENSE for the whole lump (payor side).** The money left the account once, so it records as a **single** `isSettlement` EXPENSE for the full amount, linked to every generated `DebtPayment` via the existing `payorTxnId` (all cascade payments share that one txn id). **Rejected:** one EXPENSE per debt leg (N Records lines for one real money movement — clutter, and untruthful to what happened).

6. **One INCOME for the whole lump (receiver side).** Symmetrically, the receiver's optional "add to my account" affordance adds **one** INCOME for the lump, grouped by the shared `payorTxnId`, stamping `receiverTxnId` onto all the grouped payments at once. Grouping rides the shared `payorTxnId` that already exists — **no schema needed**. The receiver leg remains optional (payor-only is a valid, fully-settled state, per ADR-0019).

7. **Atomic all-or-nothing write.** The EXPENSE plus all the `DebtPayment` rows commit in a **single database transaction** (`RoomDatabase.withTransaction` spanning the transactions and partner_debt_payments tables) — this is the app's **first true atomic multi-row write**. Because one EXPENSE backs multiple payments, a partial write would leave the ledger overstating what reached the debts (₱1,000 spent, only ₱800 credited). This is a deliberate departure from the existing sequential, best-effort pattern of `SettleDebtUseCase` (one expense = one debt, each write individually consistent) and `ApplyDebtNettingUseCase` (non-transactional loop over paired offsets), both of which are safe *because* each write stands alone — which the cascade's shared expense is not.

8. **Coexists with auto-netting, no collision.** Auto-netting is create-time, FIFO, automatic, and generates `isNetting = true` payments. The cascade is settle-time, user-driven, and generates ordinary `isNetting = false` settlement payments. The cascade only ever **reads** each debt's already-netted `remaining`; it never runs netting. The two "net"-flavored mechanisms stay separate paths and must not be conflated in code or UI.

9. **No new couples governance, no schema, no Room bump.** Either partner may record a cascade settlement unilaterally, syncing to both (identical to today's single settle) — no partner approval step. No new columns: grouping rides `payorTxnId`, atomicity is just wrapping existing writes. ADR-0009 push/pull order is unaffected.

10. **The allocation is a pure, tier-1-tested function.** Input: the ticked debts in tick order (id + remaining) and the lump amount; output: the per-debt `(debtId, amount)` split. Tested per CLAUDE.md's money-math policy — fill-in-tick-order, floor-each-at-remaining, last-debt-takes-remainder, exact-to-ceiling, and the over-ceiling block/validation.

## Consequences

- **First atomic multi-row write in the codebase** (decision 7). A future agent extending debt settlement should preserve the single-transaction guarantee, not revert to the sequential best-effort pattern the rest of the debt feature uses — the shared expense makes partial writes unsafe here specifically.
- **The UI-layer overpay block is removed** but replaced by a *domain-meaningful* ceiling (the ticked-debts total), not by unbounded overpayment. `RecordDebtPaymentUseCase`'s existing overpay tolerance is now actually exercised through the allocation path.
- **Auto-netting is untouched** and must stay a distinct path (decision 8). The user never sees the word "netting"; the cascade surfaces only `remaining` values.
- **No schema/Room migration** — grouping (both payor and receiver legs) is derived from the existing `payorTxnId`; the atomic write reuses existing DAO upserts inside one transaction.
- **Rejected alternatives:** opposing-direction overflow (decision 1); always-visible allocation list and step-by-step chain (decision 2); oldest-first fill and per-debt amount entry (decision 3); silent capping (decision 4); per-leg expenses (decision 5); best-effort sequential writes (decision 7).
