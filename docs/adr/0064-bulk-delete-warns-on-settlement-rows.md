# Bulk delete warns on settlement rows; it doesn't block or cascade

## Context

[v1.7.3 Item 7](../build/v1.7.3.md#item-7--multi-select-records-via-long-press-with-bulk-delete) (multi-select records via long-press, with bulk delete), grilled 2026-08-04. The sharp edge of the grill: a grouped debt settlement is one `isSettlement = true` EXPENSE plus N `DebtPayment` rows sharing `payorTxnId`, written atomically ([ADR-0055](0055-debt-overpay-cascade-guided-allocation.md) decision 7). Nothing reverses that write. `PartnerDebtCalculator` computes `paid` purely from payment rows and never dereferences `payorTxnId` to check the payor transaction still exists — so soft-deleting the settlement expense alone leaves the debt marked paid while the money that paid it is back in the account balance. The user gains apparent money and loses a liability, the worst direction for the error to run.

The archaeology pass that fed this decision established the corruption is **not new**. It already ships two ways: the per-row kebab menu deletes a settlement expense with no guard at all, and Reset finances ([ADR-0037](0037-reset-finances-owned-soft-delete.md)) soft-deletes *every* owned transaction including settlement legs, at unlimited scale, touching neither `partner_debts` nor `partner_debt_payments`. Bulk delete would be a volume multiplier on a live bug, not its origin.

The repository offers no way out either. `PartnerDebtRepository` has `deleteDebt` but no `deletePayment`, and `deleteDebt` itself cascades only `isNetting = true` payments — a settlement payment on a deleted debt isn't even tombstoned there. "Cascade to the payment rows" is new domain surface, not a call to an existing method.

Two ADRs pull in different directions. [ADR-0055](0055-debt-overpay-cascade-guided-allocation.md) decision 7 built atomicity specifically so the ledger never overstates what reached the debts — the invariant is defended on the write path and undefended on the delete path. [ADR-0031](0031-transfer-fee-as-cascading-linked-expense.md) decision 2 says settlement legs "deliberately don't track their parent transaction after creation," but that line is about `PartnerDebt.sourceTransactionId` (the paid-on-behalf link that *creates* a debt), not `payorTxnId` — it's a structural analogy about fire-and-forget settlement legs, not a ruling that deleting the payor leg should leave payments credited. Treating it as settled precedent for this question would overstate it.

## Decision

1. **Selecting a settlement row is allowed. The delete confirmation warns.** If the selection contains any `isSettlement` row, the confirmation dialog names the count and states plainly that deleting it returns the money to the balance but leaves the affected debt marked paid on the Partner Debt Tracker. **Rejected: blocking selection.** Blocking makes bulk delete *less* capable than the kebab menu sitting next to it, fixes nothing (the one-at-a-time path and Reset finances still produce the same corruption), and buys the appearance of safety at the cost of the feature's actual purpose — clearing out a bad import.

2. **Bulk delete does not cascade into `partner_debt_payments`.** No `deletePayment`/`retireSettlementGroup` path is built here. **Rejected: cascading the delete.** Cascading is the eventual correct end state, but it is new domain surface on a table that has never had a delete path, it converts bulk delete from a single-table write into a multi-table all-or-nothing write, and it raises questions a UI item shouldn't have to answer on its own — does the receiver's INCOME leg also retire, does the debt un-settle and reappear on the board, what does the partner's device see given `partner_debt_payments` is couple-owned and both partners write it. Those belong to a debt-feature decision, not a footnote here.

3. **Multi-table cascading would have engaged the frozen forward rule; staying single-table keeps it out of scope.** [Cross-platform-contract.md §9](../web/cross-platform-contract.md#9-atomic-multi-row-writes--android-has-a-primitive-web-doesnt) and [ADR-0063](0063-web-v1-is-online-only.md) decision 6 require any future all-or-nothing write spanning multiple tables to be designed as a `SECURITY DEFINER` RPC from the start if web needs to author it. Bulk delete over `transactions` alone, with settlement rows merely warned-and-allowed rather than cascaded, is single-table and never trips that rule. Had decision 2 gone the other way, this would have become a second §9 entry to record deliberately, not a detail to discover later.

4. **The debt-ledger corruption is explicitly not fixed by this decision.** It ships today through the kebab and Reset finances, and it continues to ship through bulk delete. Fixing it — retiring a `DebtPayment` group when its payor leg is deleted — is deliberately left to its own, separate item in the debt feature, where the fix can land once for the kebab, bulk delete, and Reset finances together, since all three funnel through the same delete path. Nobody should read Item 7 as having closed this.

5. **Adjustment rows (`isAdjustment`, [ADR-0057](0057-balance-adjustment-marked-ledger-row.md)) are allowed with no warning and no special-casing.** ADR-0057 decision 1 designed a ledger row precisely so it fails diagnosably — "there are two dated rows in Records and either partner can delete one" is the documented repair path for a double reconciliation, not a hazard the ADR overlooked. Warning here would contradict that design.

6. **This is the app's first multi-select pattern**, and its shape — long-press to enter selection, tick rows, act on the selection, scoped strictly to what's currently visible — is the precedent Notes, Recurring, and Budgets are expected to follow if they add multi-select later, rather than each inventing their own.

## Consequences

- **The known residual risk is accepted, not hidden.** For as long as the debt-ledger fix is unbuilt, a user can bulk-delete a selection containing settlements and desynchronise their debt ledger. The warning makes that visible at the moment of the delete; it does not make it impossible. This is an explicit trade, not an oversight.
- **No schema change, no Room migration.** `transactions` already carries every column this touches (`is_settlement`, `is_deleted`, `updated_at`); Room stays **v31**. The only new DAO surface is a fetch-by-id-set `@Query`, which does not affect the schema hash.
- **Section 9 stays unengaged.** The write remains single-table; no RPC is built as part of this decision.
- **Rejected alternatives:** blocking settlement rows from selection (decision 1); cascading the delete into `partner_debt_payments` (decision 2), which would have required a `SECURITY DEFINER` RPC under §9/ADR-0063 the moment web needed to author it.
