# Deleting a settlement transaction retires its DebtPayment group

## Context

[v1.7.3 Item 11](../build/v1.7.3.md#item-11--deleting-a-settlement-transaction-retires-its-debtpayment-group) — a live data-integrity bug flagged by the [ADR-0064](0064-bulk-delete-warns-on-settlement-rows.md) archaeology pass and deliberately left unfixed by it. `SettleDebtsUseCase` writes one `isSettlement = true` EXPENSE plus N `DebtPayment` rows sharing `payorTxnId` ([ADR-0055](0055-debt-overpay-cascade-guided-allocation.md) decision 7, atomic). Nothing reversed that write: `PartnerDebtCalculator.summarize` folds `paid` purely from active payment rows and never dereferenced `payorTxnId` to check the payor transaction still exists. Deleting that expense — through the per-row kebab (no guard at all) or, at unlimited scale, through Reset finances (`ResetFinancesRepositoryImpl`, [ADR-0037](0037-reset-finances-owned-soft-delete.md), which soft-deleted every owned transaction including settlement legs and touched neither `partner_debts` nor `partner_debt_payments`) — left the debt marked paid while the money that paid it was gone from the ledger. The account balance goes back up (the EXPENSE leaves the derived ledger) while the liability stays discharged: the user gains apparent money and loses a debt, the worst direction for the error to run. The mirror-image gap existed on the receiver side too: `PartnerDebtScreen` gated "add to my account" on `receiverTxnId == null`, not on that income transaction still existing, so a lender who deleted their own settlement INCOME row could never re-add it.

Two ADRs pulled in different directions on this delete path. [ADR-0055](0055-debt-overpay-cascade-guided-allocation.md) decision 7 built atomicity specifically so the ledger never overstates what reached the debts — the invariant was defended on the write path and left undefended on the delete path. [ADR-0031](0031-transfer-fee-as-cascading-linked-expense.md) decision 2 says settlement legs "deliberately don't track their parent transaction after creation," but that line is about `PartnerDebt.sourceTransactionId` (the paid-on-behalf link that *creates* a debt), not `payorTxnId` — a structural analogy about settlement legs being fire-and-forget on that other link, not a ruling that deleting the *payor leg itself* should leave its payments credited. It does not settle this question.

A derivation-side fix ("ignore payments whose payor transaction is missing") was considered and rejected: `PartnerTransactionTableSyncer.shouldPurge` hard-purges a partner transaction that is private *or* deleted ([ADR-0005](0005-partner-data-via-redacting-views.md)), so on the lender's device "transaction absent" is indistinguishable from "borrower marked it private" ([ADR-0005](0005-redacting-partner-views-for-convergence.md)). That rule would silently un-settle debts on one partner's board and not the other's.

## Decision

Fix it on the **write path** (the delete write), by retiring the payment rows, not by filtering in the calculator.

1. **`SettlementDeletionEffects`** (`feature/transactions/domain/usecase`) is a small seam owned by the transactions domain: `suspend fun onTransactionDeleted(transaction: Transaction)`, with a `NONE` no-op default. Transactions knows nothing about partner debts — only `Transaction.isSettlement` — so partner-debt implements this and Hilt binds it (`PartnerDebtModule`). This keeps the dependency pointing the way it already does (partner-debt → transactions, via `UpsertTransactionUseCase`); transactions never depends back on partner-debt.
2. **`PartnerDebtRepository` gains two new methods**, mirroring the write path's `stampReceiverTxn`: `retirePaymentsForPayorTxn(payorTxnId)` soft-deletes every active payment in that payor's group (a lump split across debts retires the whole group, not just one payment — ADR-0055's own unit); `clearReceiverStamp(receiverTxnId)` clears `DebtPayment.receiverTxnId` on every payment stamped with that income, leaving `amount`/`debtId` untouched. Both are idempotent by construction: each reads its group through a query already filtered to `isDeleted = 0` (or, for the stamp, to a matching `receiverTxnId`), so a second call finds nothing to touch.
3. **`DeleteTransactionUseCase`** is the single choke point every transaction delete funnels through — the per-row kebab today, and any future bulk delete ([v1.7.3 Item 7](../build/v1.7.3.md#item-7--multi-select-records-via-long-press-with-bulk-delete)) for free, since Item 7 is specified to reuse the same soft-delete path. It now wraps its work in one `LocalTransactionRunner.run { }` and calls `settlementEffects.onTransactionDeleted(transaction)` for every row it deletes (the transfer's fee cascade included — a no-op there, since a fee is never `isSettlement`). `PartnerDebtSettlementDeletionEffects` routes by `transaction.type`: EXPENSE → `retirePaymentsForPayorTxn`, INCOME → `clearReceiverStamp`, anything else (and any non-settlement row) → no-op.
4. **Reset finances cascades too** (captain's explicit decision, 2026-08-05) — it already soft-deletes every owned transaction, settlement legs included; leaving the debt tables alone was this exact bug at full scale. `ResetFinancesRepositoryImpl.reset()` now walks the same `settlementEffects` seam for every wiped `isSettlement` row, **inside the same `transactionRunner.run { }` block** as the transaction/account `bulkRestamp` calls, so the whole reset stays all-or-nothing. Its confirmation dialog now names the consequence in one sentence: settled debts will reappear as outstanding on the Partner Debt Tracker, for both partners.
5. **No schema change.** Room stays **v31**; no new column, no Supabase migration. The only new DAO surface is `paymentsForReceiverTxn`, a `@Query` mirroring the existing `paymentsForPayorTxn` — it doesn't touch the schema hash.
6. **The receiver-side asymmetry is accepted, not fixed.** If the borrower deletes their settlement EXPENSE, the lender's matching INCOME row (a different user's transaction, never partner-writable) is untouched — the lender still shows the income on their own ledger. Retiring across that boundary would require a cross-user write, which transactions are never allowed to be. Out of scope here.

## Consequences

- **This narrows [ADR-0037](0037-reset-finances-owned-soft-delete.md)'s scope statement.** "The reset now touches zero shared/partner data" is no longer true — `partner_debt_payments` is couple-owned, and a reset that wipes a settlement leg now retires payments in that shared table too. The affected debt reappears as outstanding on *both* partners' boards, which is the honest state, not a new leak: the money the reset just erased really did stop having paid anything down.
- **Resolves the ADR-0055 ⇄ ADR-0031 tension.** ADR-0055's atomicity invariant ("the ledger never overstates what reached the debts") now holds on the delete path too, not just the write path. ADR-0031 decision 2's "settlement legs don't track their parent transaction" is confirmed to be about `sourceTransactionId` only, as suspected — it is not disturbed by this decision, which acts on `payorTxnId`/`receiverTxnId` instead.
- **[ADR-0064](0064-bulk-delete-warns-on-settlement-rows.md) decision 4 is now closed.** Bulk delete, whenever it's built, inherits this fix for free by funnelling through the same `DeleteTransactionUseCase` choke point — no special-casing needed in that item.
- **Idempotent by construction, not by an added guard.** Deleting an already-deleted settlement finds its payment group already excluded by the `isDeleted = 0` / stamp-match filters in the retirement queries, so a second delete (or a re-run after a failed sync) is a safe no-op — no double-tombstone, no double `updated_at` bump on the payment rows (the transaction row itself still re-stamps on every delete call, a pre-existing, harmless behavior noted in the Item 7 archaeology pass).
- **`cross-platform-contract.md` §9 is not engaged by this change.** Transaction delete becomes a multi-table all-or-nothing write (`transactions` + `partner_debt_payments`), but this is Android-only application code, not a new all-or-nothing write that web needs to *author* — web v1 is online-only ([ADR-0063](0063-web-v1-is-online-only.md)) and reads the resulting rows through ordinary sync. If a future web client needs to perform this same delete itself, §9's forward rule applies then (a `SECURITY DEFINER` RPC), which is a `needs-decision` for that day, not this one.
- **Rejected:** filtering in `PartnerDebtCalculator` by checking `payorTxnId` still resolves to a live, non-deleted, non-private transaction — rejected because a partner transaction that is merely marked private is hard-purged identically to one that is deleted (`PartnerTransactionTableSyncer.shouldPurge`, ADR-0005), so this would have silently un-settled debts on one partner's device whenever the other made an unrelated transaction private, not just when they actually deleted the settlement (`PartnerTransactionTableSyncer.shouldPurge`, [ADR-0005](0005-redacting-partner-views-for-convergence.md)).
