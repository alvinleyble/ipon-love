## 🔴 F1 — Un-pushed savings contribution can permanently wedge a partner's entire sync

- **Status:** DONE `cfd1464` — three complementary layers (see below); build green, 5 new tests, full JVM suite passing. Live RLS migration confirmed applied 2026-07-03 (Alvin, via SQL Editor). Fully closed — nothing pending.
- **Severity:** High (data-flow deadlock; only recoverable by clearing app data)
- **Suggested model:** Opus, medium (touches RLS + sync-engine error semantics)

**Fix applied (all three fix directions, layered)**
1. **Sync-engine isolation** — `SyncEngine.sync()`/`pushOnly()` now push each table inside its own try/catch (`pushAllIsolated`), remember the first failure, still run the pull phase, then rethrow so error/retry semantics are unchanged. A rejected `goal_contributions` push can no longer abort the run before pull, so the client always learns the goal was unshared. (`SyncEngine.kt`)
2. **Client-side skip** — `GoalContributionTableSyncer.dirtyRows()` filters to contributions whose goal is still locally pushable (own, or shared-into-couple and not deleted), via new `SavingsGoalDao.pushableGoalIds()`. An orphaned contribution stays a benign local row instead of being retried against the server forever.
3. **RLS split** — `goal_contributions_author for all` split into per-command `select`/`insert`/`update`/`delete` policies (`schema.sql` + `migrations/2026-07-03_goal_contributions_rls_split.sql`). Goal-membership is re-validated on **INSERT only**; UPDATE/DELETE are ownership-only, so an author can always tombstone/edit their own row after the goal leaves their access.

**✅ Migration applied live** — `2026-07-03_goal_contributions_rls_split.sql` has been run against the Supabase project (`vyjaorlevomfqkidttom`); `pg_policies` for `goal_contributions` now shows the four split policies (`_select`/`_insert`/`_update`/`_delete`), confirming the old combined `goal_contributions_author for all` is gone. All three layers are live.

**Files**
- `supabase/schema.sql:513` — `goal_contributions_author` policy is `for all` with a `with check` that re-validates goal membership on **every** write (insert AND update)
- `app/src/main/java/com/iponlove/app/feature/savings/data/SavingsGoalRepositoryImpl.kt:72` — `unshareGoal` drops the goal out of the check for the non-owner
- `supabase/schema.sql:815` — `unpair()` does the same (nulls couple_id + is_shared)
- `app/src/main/java/com/iponlove/app/feature/savings/data/remote/SupabaseGoalContributionRemoteSource.kt:13` — unconditional bulk `upsert(rows)` that throws on RLS rejection
- `app/src/main/java/com/iponlove/app/core/sync/SyncEngine.kt:66` — push loop has no per-table error isolation, and push runs before pull
- `app/src/main/java/com/iponlove/app/core/sync/BaseTableSyncer.kt:58` — `push()` sends ALL dirty rows in one batch

**What happens**
The `with check` re-validates that the contribution's goal is still owned-or-shared-to-me on every write. When the owner un-shares or the couple unpairs, a non-owner contributor's already-written local contribution row no longer satisfies the check. On the next sync, the bulk upsert is rejected → throws → the whole `sync()` aborts before the pull phase.

**Repro (Alvin + Patty)**
1. Alvin shares goal G with Patty.
2. Patty opens G and adds a ₱500 contribution while offline (or racing Alvin) → local row, `pending_sync=true`.
3. Before Patty's push lands, Alvin un-shares G (or they unpair).
4. Patty reconnects → `goal_contributions` push is RLS-rejected → `sync()` throws → she never reaches pull (never learns G was unshared), row stays `pending_sync=true` **forever**.
5. Every subsequent sync repeats the throw. Because the batch is one statement, it also blocks **all** of Patty's other pending writes. She cannot even tombstone the poisoned row (same `with check` rejects the UPDATE). Only clearing app data recovers.

**Fix direction (pick one or combine)**
- Scope the `with check` membership requirement to **INSERT only**, so an author can always UPDATE/tombstone their own row (`for insert with check (...)` + a separate `for update using (user_id = auth.uid())`).
- Client-side: skip pushing a contribution whose local goal no longer exists / is no longer shared-or-owned.
- Give the push loop per-table (or per-row) error isolation so one rejected table can't abort the whole sync.

**Tests to add**
- Repo/syncer test: a contribution to a now-unshared goal does not wedge the push (or is skipped).
- (If RLS changed) document the INSERT-vs-UPDATE split in the ADR-0025 notes.

**Verify on device:** contribute to a shared goal, unshare from the other device, confirm the contributor's sync still completes and other pending writes flush.

## 🔴 F2 — First-time PIN setup immediately locks the user out

- **Status:** DONE `480dabb` — `appLockManager.unlock()` called in `confirmSet()` after `setPin()` succeeds; `AppLockManager` injected into `AppLockSetupViewModel`. 2 new ViewModel tests, full JVM suite green (build compiles, all tests pass).
- **Severity:** Medium-High (hits 100% of first PIN setups; recoverable with one PIN entry but looks broken)
- **Suggested model:** Sonnet, low (one-line-ish fix)

**Files**
- `app/src/main/java/com/iponlove/app/feature/applock/presentation/AppLockManager.kt:23` — `_isLocked` starts `true`; only `unlock()` clears it
- `app/src/main/java/com/iponlove/app/feature/applock/presentation/AppLockViewModel.kt:50,57,78` — `unlock()` is called ONLY from the lock screen
- `app/src/main/java/com/iponlove/app/MainActivity.kt:192` — gate is `appLockPrefs.isPinSet && isLocked`
- `app/src/main/java/com/iponlove/app/feature/applock/presentation/AppLockSetupViewModel.kt:72` — sets PIN but never calls `unlock()`

**What happens**
In any session started without a PIN, `_isLocked` stays `true` the whole time (the lock never renders because `isPinSet` is false). The moment the user finishes first-time PIN setup, `isPinSet` flips true → gate becomes `true && true` → the lock Dialog appears **over the setup screen**, demanding the PIN they just created. The biometric-nudge dialog fires in the same cascade, so their z-order is also nondeterministic.

**Repro**
Fresh install (or any no-PIN session) → use app normally → Settings → Security → set PIN "1234" → confirm → lock screen appears instantly, must re-enter 1234.

**Fix direction**
Call `appLockManager.unlock()` on `pinSetSuccess` — a freshly-set PIN means the user is present and just authenticated, so the session should start unlocked. (Inject `AppLockManager` into `AppLockSetupViewModel`, or trigger unlock from the setup screen's `pinSetSuccess` effect.) Double-check the biometric-nudge dialog no longer collides.

**Tests to add**
- ViewModel test: after `confirmSet` success, the manager is unlocked. (Manager may need to be injectable/fakeable.)

**Verify on device:** fresh install → set PIN → you land back in the app unlocked (no immediate lock); background 30s → lock engages correctly on the *next* return.

## 🟠 F3 — Ex-partner's contributions resurface & double-count when re-sharing a goal to a new partner

- **Status:** DONE `5c3b67a` — view-level fix (audit option B). `partner_goal_contributions` now nulls `amount`/`note`/`date` when the contributor is no longer a member of the goal's couple (`gc.user_id not in (select id from users where couple_id = g.couple_id)`); the existing mapper folds null-amount → `isDeleted`, so the stale replica is purged via the normal path. Same-couple unshare→reshare is unaffected. **Zero Kotlin changes** — pure SQL redaction, so no new JVM test is possible; verification is the documented manual SQL check in the migration. `schema.sql` view + comment updated; migration `supabase/migrations/2026-07-03_partner_goal_contributions_membership.sql`; ADR-0025 point 5 gets an F3 addendum. **Migration applied to live Supabase and confirmed via `pg_get_viewdef`** — the membership `NOT IN` clause is present on all three redaction cases. Build unaffected (no app code touched).
- **Severity:** Medium (privacy leak of ex-partner's amount + note text, plus silent miscount)
- **Suggested model:** Opus, medium (data-model / RLS-view reasoning)

**Files**
- `supabase/schema.sql:815` — `unpair()` reverts the goal to personal but leaves contributions untouched ("benign orphans")
- `supabase/schema.sql:658` — `partner_goal_contributions` view gates visibility purely on the goal's **current** `couple_id`
- `app/src/main/java/com/iponlove/app/feature/savings/data/SavingsGoalRepositoryImpl.kt:68` — `shareGoal` reuses the same goal id

**What happens**
Because the view only checks the goal's current `couple_id` (not whether the contributor was ever in that couple), re-sharing an old goal into a **new** couple resurfaces the ex-partner's old contribution rows — amount and note — to the new partner, and re-adds them to the derived `savedAmount` on both devices.

**Repro (Alvin + Patty, then Alvin + Charlie)**
1. Alvin + Patty share goal G; Patty contributes ₱500 with note "from my bonus".
2. They unpair.
3. Alvin later pairs with Charlie and re-shares the **same** goal G.
4. Charlie's device replicates Patty's ₱500 + note; the goal total is inflated on both Alvin's and Charlie's devices.

(Un-share then re-share to the **same** couple is correct — Patty's contribution legitimately still counts. The bug is specifically re-sharing to a *different* couple.)

**Fix direction (pick one)**
- `unpair()` soft-deletes (or disassociates) contributions authored by the departing partner.
- The `partner_goal_contributions` view additionally verifies the contributor is a current member of the goal's couple.

**Tests to add**
- Migration/view test or documented manual SQL check for the re-share-to-new-couple case.

**Verify on device (needs 3 accounts or reused test accounts):** the re-pair-and-reshare sequence above; confirm the new partner does NOT see the old contribution and the total is correct.

## 🟠 F4 — Onboarding gate reads a stale/in-flight sync state (race)

- **Status:** DONE `fe3b6ea` — `SyncEngine.sync()` now single-flights via a published `CompletableDeferred<Boolean>` (`currentRun`): a coalesced call awaits *that run's* actual terminal result (propagating its exception on failure) instead of returning `false` immediately. `pushOnly()`/`pullOnly()` clear `currentRun` when they take the lock so a coalescing `sync()` can't misread an unrelated older sync's leftover result. `MainActivity`'s onboarding gate now does `val syncSucceeded = runCatching { syncEngine.sync() }.getOrDefault(false)` instead of sampling `syncEngine.state.value`, so it always reflects the outcome of the run it actually raced with — no more premature `Syncing` read or stale prior-user `Success`. Build green, 2 new `SyncEngineTest` cases + 1 updated, full JVM suite passing. Verified live on device (multi-account emulator testing) — see **F10** for a related device-scoped-onboarding bug this verification also surfaced and fixed.
- **Severity:** Medium (new users intermittently skip onboarding; account-switch can double-fire it)
- **Suggested model:** Sonnet, low-med

**Files**
- `app/src/main/java/com/iponlove/app/MainActivity.kt:144` — `runCatching { syncEngine.sync() }` then `val syncSucceeded = syncEngine.state.value is SyncState.Success`
- `app/src/main/java/com/iponlove/app/MainActivity.kt:105` — `onStart` observer fires a **concurrent** `sync()` on every foreground
- `app/src/main/java/com/iponlove/app/core/sync/SyncEngine.kt:59` — `sync()` is single-flight (`tryLock` → returns `false` if coalesced)

**What happens**
The gate ignores the `Boolean` that `sync()` returns and instead samples the process-global `syncEngine.state.value`. Because `onStart`'s concurrent sync usually wins the single-flight lock first, the gate's own call coalesces (returns immediately) and then reads `Syncing` → `syncSucceeded=false` → onboarding silently skipped for a genuine new user. Conversely, on an in-process account switch, `state` can still hold the previous user's `Success` → onboarding fires for an existing user (the exact false-positive slice 3 was designed to prevent).

**Note:** the narrower partial-pull races are NOT reachable — `pull()` failures cancel the whole `coroutineScope` and rethrow, so `SyncState.Success` genuinely implies every table pulled. The defect is purely the coalesced/stale **read**.

**Repro**
New user who reaches onboarding but kills the app before finishing (`onboardingDone=false`, 0 owned rows). On relaunch the session is restored, so `onStart` fires authenticated and starts a sync concurrently with the gate's `LaunchedEffect`; when `onStart` wins the lock, the gate reads `Syncing` and onboarding is skipped. Nondeterministic ("onboarding sometimes doesn't show").

**Fix direction**
Tie the decision to **this login's** run — e.g. use the `Boolean` returned by `sync()` (and, when it coalesces, await the in-flight run's terminal state), rather than sampling the shared `state`. Consider resetting `SyncEngine.state` per user, or deriving `syncSucceeded` from a per-run result.

**Tests to add**
- ViewModel/logic test around the gate: coalesced sync must not read as "succeeded" prematurely; stale `Success` from a prior user must not gate a new user.

**Verify on device:** new-user onboarding shows reliably across repeated cold starts; sign out → sign in as a different existing user does not re-show onboarding.

## 🟡 F5 — Duplicate partner-debt on process death during "Paid for partner" save

- **Status:** DONE `38d102f` — `debtId` default now `DeterministicUuid.v5("paid-on-behalf:${transaction.id}")` instead of a random UUID, so a re-save after mid-save process death upserts the same debt row instead of creating a second one. 1 new test (`defaultDebtId_isDeterministicFromSourceTransaction_soReSaveDoesNotDoubleCount`), full JVM suite green (537 tests).
- **Severity:** Low-Med (money correctness; narrow window — requires process death mid-save)
- **Suggested model:** Sonnet, low

**Files**
- `app/src/main/java/com/iponlove/app/feature/partnerdebt/domain/usecase/PaidOnBehalfUseCase.kt:31` — `debtId` defaults to a random UUID; the debt already carries a stable `sourceTransactionId` (line 49)
- `app/src/main/java/com/iponlove/app/feature/transactions/presentation/AddTransactionViewModel.kt:168` — caller passes no `debtId`; `clearDraft()` runs *after* the writes (line 178)

**What happens**
The transaction id is stable across process death (mirrored in the draft), so re-saving re-upserts the same transaction idempotently. The debt id is not — it's a fresh random UUID each call. If the process dies between the debt commit and `clearDraft()`, the draft (with `paidForPartner=true`) survives; on relaunch the route restores and a second Save creates a **second** PartnerDebt, double-counting what the partner owes.

**Fix direction**
Derive a deterministic `debtId` from the already-stable `sourceTransactionId` (e.g. `DeterministicUuid.v5("paid-on-behalf:$transactionId")`) so re-save is idempotent — or `clearDraft()` before the writes. The deterministic-id approach is cleaner and consistent with the netting/recurring id pattern.

**Tests to add**
- `PaidOnBehalfUseCaseTest`: two invocations for the same source transaction produce one debt (deterministic id).

## 🟠 F10 — Onboarding flags were per-device, not per-account: a second account on a shared device silently skipped onboarding (incl. seeding)

- **Status:** DONE `54573fa` — reclassified `onboardingDone`/`pairingCardDismissed` from per-device to per-account. `LocalDataWiper.wipe()` now also calls `OnboardingRepository.reset()` (which clears the DataStore) alongside Room/cursors/nav config, so sign-out and account-switch (`AccountSwitchGuard`) both reset it, same as everything else `LocalDataWiper` owns. ADR-0024 gets a dated addendum documenting the reversal and rationale. Build green, 4 new tests (`OnboardingRepositoryImplTest` + updated `LocalDataWiperTest`), full JVM suite passing. Verified live on device: a genuinely-new third account (`testdev3`) now correctly gets the onboarding graph after two other accounts had already completed it on the same emulator.
- **Severity:** Medium (silent, no crash — a second real account lands in a fully empty app with no accounts/categories and no explanation; likely rare in production since partners normally use separate devices, but real for shared/family devices and guaranteed on any dev/QA device reused across test accounts)
- **Discovered:** during F4's on-device verification (Alvin manually cycled 4 test accounts on one emulator to force the sync-coalescing race; account #3 unexpectedly skipped onboarding)
- **Suggested model:** Sonnet, low-med (mechanical — extends `LocalDataWiper`'s existing reset pattern to one more DataStore; the only non-mechanical part was confirming with Alvin that reversing the ADR-0024 "per-device" call was actually wanted, since it was a deliberate documented decision, not an oversight)

**Files**
- `app/src/main/java/com/iponlove/app/feature/onboarding/di/OnboardingModule.kt:22-23` — had an explicit comment: "Deliberately not touched by LocalDataWiper ... per-device, not per-account (ADR-0024)"
- `app/src/main/java/com/iponlove/app/feature/onboarding/data/OnboardingRepositoryImpl.kt` — `onboarding_prefs` DataStore, singleton, survives sign-out
- `app/src/main/java/com/iponlove/app/core/session/LocalDataWiper.kt` — wiped Room + sync cursors + nav config on sign-out/account-switch, but not this DataStore
- `docs/adr/0024-first-run-onboarding-gated-on-post-sync-emptiness.md` — addendum added

**What happened**
`ShouldShowOnboardingUseCase` checks `onboardingRepository.isOnboardingDone()` *before* the post-sync-emptiness check, and that flag lived in a DataStore singleton never touched by `LocalDataWiper`. Once any account completed onboarding on a device, the flag stayed `true` forever, regardless of which account was later signed in — so every subsequent different account short-circuited straight past onboarding, including the starter-template seeding step, and landed in an app with zero accounts/categories.

**Repro (as found)**
1. `testdev2` signs in on a device, completes onboarding → `onboarding_done = true`.
2. `testdev2` signs out (clean sign-out, wipe runs) → flag survives.
3. `tfvin24` (an account that had *already* onboarded previously, for real) signs in → correctly no onboarding — but only by coincidence.
4. A genuinely brand-new account (`testdev3`) signs in on the same device → local Room confirmed empty (0 rows across `users`/`accounts`/`categories`), sync succeeds, but onboarding is skipped anyway because the stale flag from step 1 is still `true`.

**Fix applied:** `LocalDataWiper.wipe()` now resets onboarding state too — see Status.

**Tests added**
- `OnboardingRepositoryImplTest.reset_clearsOnboardingDone_andPairingCardDismissed` (+ 3 baseline coverage tests for the repo, which had none before).
- `LocalDataWiperTest` updated to assert `onboarding.reset()` is called alongside the other three resets.

## ✅ Verified clean (examined, no bug — don't re-investigate)

- **Conflict resolution / redaction:** partner mappers handle redacted (null) columns safely; such rows are always purged by `shouldPurge`; no NPE.
- **Bidirectional contribution counting:** own vs. partner contributions are disjoint sets (base pull vs. redacting view), distinct random UUIDs, summed once each — no double-count on concurrent adds. (The random-UUID mechanism is sound in isolation; F1 is an RLS/ordering interaction, not a collision.)
- **`SavingsGoalCalculator`:** all-BigDecimal, correctly excludes soft-deleted contributions and orphans.
- **`unpair()` reconciliation:** no drift (see F9 note).
- **PurgePartnerReplicaUseCase:** purges both savings tables + resets both cursors on unpair; partner-goal syncer cascades a contribution purge.
- **RLS insert path:** correctly allows a partner to insert against a shared goal they don't own, while blocking insert against a non-shared / non-owned goal.
- **App-lock grace-period timer:** wired to `onStop`/`onStart` (not `onPause`), so the biometric prompt and permission dialogs don't spuriously lock or reset the timer.
- **PIN stale-fill:** `pin` cleared on every re-lock and on verify (success + failure); no lingering 4-length auto-submit.
- **Biometric fallback/lockout:** all error codes (incl. `ERROR_LOCKOUT`/`ERROR_LOCKOUT_PERMANENT`) route to the PIN pad; `showPinPad` is `rememberSaveable`; the auto-launch `LaunchedEffect(Unit)` fires once per lock, no loop; PIN pad always reachable.
- **Transaction draft/txn-id isolation:** per-id routes = distinct `SavedStateHandle`s; editing A then B can't hydrate B with A's draft.
- **Notes re-seed race:** `contentSeeded` guard + `setHtml(draftHtml ?: initialHtml)` prefers saved draft; `snapshotFlow` captures latest HTML; `save()` reads `richTextState.toHtml()` directly — no keystroke loss, no clobber.
- **Lock-Dialog stacking / BackHandler:** lock Dialog stacks above every dialog opened before it; no Flow-driven dialog auto-opens while locked; `dismissOnBackPress=false` swallows Back so the note editor's `BackHandler` doesn't fire under the lock. (Only exception: F2's near-simultaneous nudge dialog.)
- **Nav understudy dedupe:** pinning both Couple and Manage collapses to one Manage when unpaired and restores Couple on re-pair; saved `NavConfig` is never mutated by the display-time substitution. Editor can't double-pin Manage.
- **Kill-mid-onboarding:** no double-seed — `countOwned > 0` after seeding blocks re-onboarding regardless of the flag, and `SeedStarterDataUseCase` uses deterministic-UUID upserts anyway.
- **Failed pairing during onboarding:** every exception → `PairingException` → error banner, stays on the fork; no half-applied `couple_id`.

**Minor (very low, noted only):** `countOwned` excludes soft-deleted rows, so a user who soft-deletes *every* category and account and never completed onboarding (`onboardingDone=false`) would be re-onboarded. Marginal. Also: stale doc comments referencing "Settings non-pinnable" in `NavConfig.kt`/`NavResolver.kt`/`IponApp.kt` — cosmetic, Settings is intentionally pinnable per ADR-0026.
