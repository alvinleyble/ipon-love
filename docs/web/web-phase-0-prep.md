# Web Phase 0 — Design + base-app/backend prep

**Charter (set 2026-07-26):** the running ledger for the web-app track's first phase — the web-side sibling of a native `vX.Y.md` doc. Same rule: every change we decide on gets booked here as a numbered item **first** (state, request, open design tensions), so nothing slips between conversations. Web items are numbered **W#** to keep them distinct from the native global counter.

**Origin:** a 2026-07-26 "what must change in the base app before the Q4 web app?" audit (recorded in [web-build-progress.md](web-build-progress.md#origin-2026-07-26)). Every item below is **booked, not yet grilled** — this doc records the ask + the tensions; grilling produces the locked design (an ADR in the shared `docs/adr/` sequence, or a filled section of [cross-platform-contract.md](cross-platform-contract.md)).

**Two buckets:** W1/W3/W4/W5/W6 are **base-app / backend changes** (execute as native/Supabase slices, book into the in-flight native version doc when built too). W2 is the **contract spec**. W7/W8/W10 are **web-app design** proper.

**Suggested grill order:** W1 and W2 first (highest leverage, both block real risk). W3/W4 are decisions that shape the schema, so settle before web greenfield (W8). W5/W6 are contract line-items that can fold into W2's grill. W7 folds into W1's. **W9** folds into whichever of W1/W3 resolves first (see the note below).

**Architecture direction locked 2026-07-28 (conversation, not yet a formal `/grill` pass — see W8/W10):** the web app's domain/data/sync layer will be **shared with Android via Kotlin Multiplatform** (Kotlin/JS target) rather than hand-reimplemented in TypeScript against the W2 contract. Native React/Tailwind UI on top, nothing shared at the UI layer. This changes **W2's role** (see its entry) and **W8's stack proposal** (rewritten below), and adds **W10** (the actual extraction work — booked, not scheduled yet). Driven partly by a longer-horizon consideration: Alvin expects to afford the $99/yr Apple Developer fee in a couple of years, and the same shared module extends cleanly to an `iosMain` target later, so this isn't just a web-specific bet.

**Cross-cutting note (added 2026-07-28): Supabase's first edge function is already committed, independent of web.** The AI-companion paywall design (Horizon #3, `subscription-paywall-design.md` D8) already decided AI credits must be **server-metered** via a Supabase Edge Function — "paid credits can't be tracked client-side," the same trust-boundary argument as **W1**'s entitlement-column problem. This means the "should Supabase get its first edge function" question this doc keeps treating as open (W1's validating write path, W3's server-side materialization option, W9's server-side notification generation) **isn't actually a from-scratch infra decision** — it's already going to happen for AI, on whatever timeline Horizon #3 builds. Whichever lands first (AI credits, or W1's entitlement lock) should design its edge-function plumbing (auth, deployment, invocation pattern) with the others in mind, so the second and third consumers are cheap follow-ons rather than three separate one-off builds.

## W1 — Lock the entitlement columns (RLS + validating write RPC)

- **Status:** ✅ **GRILLED 2026-07-29 → [ADR-0060](../adr/0060-entitlement-columns-are-rpc-write-only.md)**, design locked, **booked for native execution as [v1.7.2.md Item 1](../build/v1.7.2.md#item-1--lock-the-entitlement-columns-rls--validating-write-rpc-from-web-phase-0-w1)** (Opus/high, not yet built). Confirmed as a backend **+ client** change: column-level `REVOKE` on the four entitlement columns, one `SECURITY DEFINER` RPC as the sole write path, and a client change forced by the `users` push being a full-row upsert (a locked column can't even be *named* in the statement, so ordinary profile edits would break otherwise). **Receipt validation is deliberately deferred** — the RPC is a passthrough, so this closes the door without locking it; verification must precede enforcement flip-day, W7, or AI, whichever is first. The open tensions listed below are all resolved in ADR-0060; kept here as the record of what the grill was asked to settle.
- **The problem:** `users_update` RLS is `using (id = auth.uid()) with check (id = auth.uid())` — a user can write **any** column on their own row, including `is_premium` / `premium_until` / `entitlement_source` (schema.sql:73-75). ADR-0044 knowingly accepts this as a "client-trusted advisory column": on Android you'd need to root the device or MITM TLS to exploit it, so the risk is low. **On web that assumption collapses** — anyone opens dev tools and runs `supabase.from('users').update({ is_premium: true })`, which then syncs back to their phone via our own sync engine. Couple governance (either-partner-unlocks) means one forged row unlocks both.
- **Open design tensions to grill:**
  - How to lock the three columns while keeping the row self-updatable for legit fields (`accent_color`, `avatar_motif`, display name, etc.)? Options: column-level `UPDATE` privilege revocation; a `BEFORE UPDATE` trigger that rejects entitlement-column changes unless the write comes from a `SECURITY DEFINER` context; splitting entitlement into a sibling table only an RPC can write.
  - The legit write path becomes a **receipt-validating RPC** (Play receipt for Android; whatever web uses for W7). What validates a Play purchase server-side — an edge function calling Google's API, or a trusted server component? (Supabase has **no** edge functions today — this would be the first.)
  - Interaction with ADR-0044's **offline-first / fail-open cold-start** and **cache-of-Play** design — the client still needs to *read* entitlement offline; only *writes* get locked. Confirm the cache/read path is untouched.
  - The `entitlement_source = 'GRANT'` beta-comp path (schema.sql:1209) and how it's set today — must survive the lockdown.
  - Migration/rollout: existing legit `is_premium=true` rows must not break.
- **Ties to:** W7 (web purchase path feeds the same RPC). ADR-0044, `subscription-paywall-design.md`.

## W2 — Freeze the cross-platform contract (determinism + sync protocol + money math)

- **Status:** ✅ **DONE 2026-08-05** — [cross-platform-contract.md](cross-platform-contract.md) is **FROZEN**, §1–§9, with exactly one sanctioned pending line (§7.5's allowed web origin, blocked on the hosting choice in W8). Grilled 2026-08-03 (sequencing and §9 — outcome at the end of this entry); filled and frozen 2026-08-05 as [v1.7.4.md Item 1](../build/v1.7.4.md#item-1--freeze-the-cross-platform-contract-from-web-phase-0-w2), shipping the load-bearing deliverable: [`CrossPlatformContractConformanceTest`](../../app/src/test/java/com/iponlove/app/core/util/CrossPlatformContractConformanceTest.kt), 15 JVM tests asserting the §1 UUID vectors (23 name→id pairs incl. the full starter catalog), the §1b composite-id forms and the §4 per-site rounding. **The W10-phase-2 precondition is therefore met.** Also **booked for native execution as [v1.7.4.md Item 1](../build/v1.7.4.md#item-1--freeze-the-cross-platform-contract-from-web-phase-0-w2)** (2026-07-29, Opus/high — booked into v1.7.2 first, moved to v1.7.3 the same day so it wouldn't hold up cutting the W1 release, then to v1.7.4 on 2026-08-03 when the web track was split into its own build doc). Skeleton exists: [cross-platform-contract.md](cross-platform-contract.md). **§8 is now answerable** — W1 shipped as [v1.7.2.md Item 1](../build/v1.7.2.md#item-1--lock-the-entitlement-columns-rls--validating-write-rpc-from-web-phase-0-w1) / [ADR-0060](../adr/0060-entitlement-columns-are-rpc-write-only.md), so the entitlement-write RPC contract exists to be frozen rather than guessed at. **Role changed 2026-07-28 by the KMP decision (see W10):** the sections below (UUID schemes, LWW rule, FK order, money rounding) were originally meant to be a spec a *separate* TypeScript implementation must hand-follow exactly — under the shared-module plan, that same logic instead moves into `commonMain` and is **compiler-enforced identical** by construction, not just documented as identical. This doc **doesn't go away** — it's still the one place these invariants are written down (useful for onboarding, audits, and for whatever genuinely stays platform-specific, e.g. §7 image compression, §9 atomic writes), but it's no longer the thing standing between "correct" and "silently diverged" for the pieces that move into `shared`. The pre-grill guidance here was to wait until W10 clarified exactly which pieces move — **the grill overturned that, see the outcome below.**
- **✅ Grill outcome (2026-08-03) — proceed now, don't wait for W10.** The wait was circular: this contract waited on W10, W10's own entry says start it closer to when the web build begins, and the web build is the thing that needs the contract — nothing broke the tie, so "wait" resolved to "never." Two findings forced it:
  - **The web track is next up after receipt OCR and could begin within 48 hours**, so the pre-extraction window this doc assumed would be long is effectively gone.
  - **`DeterministicUuid` is not `commonMain`-ready**, contradicting W8's "already written in `commonMain`-compatible style" claim (corrected in W8/W10 below). Sharing it is a **rewrite onto different SHA-1 and UUID primitives, not a file move** — and a rewrite that byte-orders the namespace differently silently produces different ids, i.e. duplicate rows instead of merged ones.
  - **Consequence for scope:** the conformance vectors are the load-bearing deliverable, not the prose. They are the regression harness proving the extraction did not change behavior, so they must exist **before W10 phase 2** (the phase that actually moves the logic). W10 phase 1 (empty module + Kotlin/JS target, zero behavior change) can run in parallel — the two tracks only have to meet in that order.
  - **§9 is settled by this grill** (web v1 is online-only → grouped multi-debt settlement stays Android-only; see [ADR-0063](../adr/0063-web-v1-is-online-only.md) and contract §9). **§7 freezes except its allowed-web-origin line**, which genuinely cannot be pinned until hosting is chosen.
- **Why it still matters:** for whatever stays platform-specific, or for the period before W10 is built, the same silent-failure risk applies — getting any of these wrong fails **silently**, no crash, just duplicated rows or centavo-divergent numbers weeks later.
- **What must be pinned (each a section in the contract doc):**
  - **Deterministic v5-UUID schemes** — namespace `9d8f6c2e-5b1a-4f3d-9e7c-1a2b3c4d5e6f`, SHA-1/v5 (not v4, not JDK v3/MD5), RFC-4122 variant, and every `name` string verbatim: recurring `"${ruleId}:${date}"`, netting `"netting:${a}:${b}"`, paid-on-behalf `"paid-on-behalf:${txnId}"`, transfer-fee category `"builtin-category:transfer-fee:${userId}"`, starter `"starter-category:${userId}:${key}"` / `"starter-account:${userId}:${key}"`. Source: [DeterministicUuid.kt](../../app/src/main/java/com/iponlove/app/core/util/DeterministicUuid.kt) + its 6 call sites.
  - **LWW write rule** — `updated_at = max(now() + clockOffset, prev + 1ms)`, offset-corrected + monotonic (ADR-0001); clock-offset acquisition; `pending_sync` outbox flag (ADR-0002). Web must not write naive timestamps.
  - **FK push/pull order** (ADR-0009): `users → couples → accounts → categories → recurring_rules → transactions → budgets → notes → note_images` (+ partner variants, + the newer leaves: savings_goals/goal_contributions/transaction_images, and the notification inbox at the *end* per ADR-0053). Confirm the authoritative full ordering.
  - **Money math** — canonical storage `numeric(14,2)`; wire format is `double` (`BigDecimalSerializer`, `PrimitiveKind.DOUBLE`); all money aggregates are **derived per-client** (balance ADR-0007, analysis, budget %, debt splits). Pin the exact scale + rounding mode (HALF_UP, scale 2) so web (decimal.js, not native floats) matches to the centavo.
  - **Conflict resolution** — row-level LWW by `updated_at`, except shared notes (conflict copy, ADR-0003); partner-row purge-on-unshare/delete (ADR-0005); `EnsureCurrentUserRow` before any write (ADR-0013); couple ops are RPC-only (ADR-0006/0008).
- **Ties to:** absorbs W5 (seeding) and W6 (images) as line-items; every native ADR listed above.

## W3 — Recurring materialization + notification evaluation: server-side vs. web-reimplementation

- **Status:** BOOKED, needs grill/decision. Model TBD (server-side path = new Supabase edge function + pg_cron, first of their kind here).
- **The problem:** these jobs run *only* on the Android device today, via WorkManager, with **no server counterpart** — Supabase has no cron or edge functions (only `server_rev` triggers, RLS, couple RPCs). A user living on web for two weeks would get none of this until they reopen the phone. As of 2026-07-28 (v1.7.1) the inventory is now **three** client-only evaluators, all sibling-pattern workers off the same two enqueue sites (`MainActivity`'s post-sync `LaunchedEffect`, `SyncWorker`'s post-sync tail):
  - [RecurringScheduler](../../app/src/main/java/com/iponlove/app/feature/recurring/domain/usecase/RecurringScheduler.kt) — materializes due recurring occurrences (deterministic ids make this convergent even if web reimplements it independently, see [W2 §1](cross-platform-contract.md#1-deterministic-uuids--the-convergence-mechanism)).
  - `BudgetAlertWorker` — evaluates the three-rung budget thresholds (warn/limit/over, ADR-0054), writes inbox rows.
  - `RecurringReminderWorker` — due-date nudges for confirm-on-arrival rules (ADR-0052), writes inbox rows.
  - `PartnerDebtNotificationWorker` — partner-authored-debt detection (v1.7.1 Item 9), writes inbox rows.
  - (ADR-0056, 2026-07-28, opt-in): an off-app `PeriodicWorkRequest` sweep was added for `RecurringReminderWorker` specifically — still 100% client-side/WorkManager, not a server job; doesn't change this item's calculus, just widens *when* the Android client itself fires.
- **Known native latency gap (context, not yet booked as a native item):** all three workers above enqueue only once per process launch + the sync tail — a budget alert triggered by *your own* transaction (crossing 80%, still using the app) doesn't fire until the next launch or a sync, not immediately. Noted at Item 12's grill (v1.7.1.md line 13) as a "v1.7.2 candidate, not booked." Irrelevant to *whether* this becomes server-side, but if W3 stays client-only, web shouldn't inherit the same launch-only trigger gap without at least flagging it.
- **Key nuance (softens the urgency):** materialized occurrences use **deterministic ids** (`ruleId:date`), so if the web client *also* materializes with the identical id scheme (W2), the two **converge** — no double transactions. So correctness does **not** force a server-side move; it's a choice between (a) porting the date math to JS/TS *twice* (drift risk) vs. (b) centralizing it server-side once (cleaner, but introduces the app's first edge function + cron and a "who's the writer" question under LWW).
- **Open tensions to grill:** confirm-on-arrival vs. auto-post rules (only auto-post could safely be server-materialized without a user action; confirm-required stays a client/user event); budget alerts are inherently a *notification* concern (already routed through the synced inbox, ADR-0053) — does web need its own evaluation, or does moving evaluation server-side unify both clients? Timezone/`asOf` definition across clients (MonthWindow logic).
- **Ties to:** W2 (deterministic-id parity is the enabler either way), ADR-0012 (background job ownership), ADR-0053 (inbox already synced).

## W4 — DataStore preferences: decide per-device vs. synced

- **Status:** BOOKED, needs decision (light grill). Per-pref call; some become a synced table/columns (native + web read them), some stay local by design.
- **The problem:** these live only in Android DataStore, so they don't follow the user to web:
  - **Correctly per-device (do NOT sync):** app-lock PIN/biometric, sync cursor, clock offset, sync status, widget session, last-active-user.
  - **Product call (user may expect them to follow):** theme *palette* (note `accent_color` already syncs on `users`; the rest doesn't), navbar layout, global privacy/amount-mask default, notification prefs — incl. the Item 2-4 (native v1.7.1) budget thresholds + per-budget mutes, which were *deliberately* made **local per-device** (ADR-0054) — revisit under a web lens, tutorial/onboarding progress.
- **Open tensions to grill:** which prefs graduate to a synced `user_preferences` table (or columns on `users`)? For the ones that stay local, web just starts at defaults — acceptable, but confirm per pref. Note ADR-0054 explicitly chose local for budget thresholds/mutes on the reasoning that cross-device dup is prevented by slot-name dedup, not by syncing settings — that reasoning predates committing to web as a first-class surface; re-examine.
- **Ties to:** ADR-0014 (personalize is local preview + DataStore), ADR-0054 (local notification prefs), ADR-0053.

## W5 — Starter-seeding guard parity

- **Status:** ✅ **DONE 2026-08-05** — absorbed and frozen as [cross-platform-contract.md §6](cross-platform-contract.md#6-onboarding--starter-data-seeding). The four-clause guard predicate is pinned, and the ruling is that **web may seed but must run the guard against server state** (rejected: "web never seeds" — it would leave a web-first signup with nothing). No native change was needed, as expected.
- **The problem:** [SeedStarterDataUseCase](../../app/src/main/java/com/iponlove/app/feature/onboarding/domain/usecase/SeedStarterDataUseCase.kt) upserts starter categories/accounts on deterministic ids (`starter-category:$userId:$key`) and **overwrites in place** — it does *not* itself check tombstones. The guard against re-seeding lives **upstream**, and it checks the **server** ("has this user already onboarded?"), explicitly *not* local emptiness (a comment in MainActivity notes local emptiness would "duplicate-seed a reinstall/second device"). The web client has empty local state by definition — if it naively seeds on first run, it **resurrects starter rows the user already deleted**.
- **What web must do:** replicate the same server-side "already onboarded?" check before seeding, and honor tombstones. Pin the exact guard condition in the contract.
- **Ties to:** W2, ADR-0013 (users-row-first), the deterministic-id merge behavior.

## W6 — Image pipeline parity (compression, private buckets, storage RLS, orphans)

- **Status:** ✅ **DONE 2026-08-05** (one line deferred) — absorbed and frozen as [cross-platform-contract.md §7](cross-platform-contract.md#7-image--attachment-pipeline): bucket/path conventions with `folder[1]` as the RLS key, compression targets (1080 px / 1440 px, JPEG 85), the authenticated-URL scheme plus the mandatory legacy `/object/public/` rewrite, the full storage-RLS map, and an upload-then-write-row orphan rule for web. **Verified no new storage policy is needed** — the existing policies key on `auth.uid()` / `auth_couple_id()` from the JWT, which a browser session resolves identically. **⬜ Still pending:** the allowed web *origin* for storage CORS, blocked on the hosting choice in [W8](#w8--web-app-greenfield-foundational-design) — the sole sanctioned unfrozen line in the whole contract. Good news: attachments store a `storage_url` (not a local path) in `note_images`/`transaction_images` (schema.sql:273-297), and files live in **private** buckets (`receipts`, `note-images`, `couple-banners`) fronted by authenticated URLs — so web *can* render them.
- **What web must replicate / what to verify:**
  - Client-side **compression** ([CompressReceiptUseCase](../../app/src/main/java/com/iponlove/app/feature/transactions/domain/usecase/CompressReceiptUseCase.kt)) + the same bucket/path naming convention on upload.
  - **Authenticated access** — private buckets resolve only with the token attached (StorageAuthInterceptor pattern). Confirm storage RLS/policies admit the web origin (CORS + policy).
  - An **orphan-cleanup** story — the Android app sweeps `filesDir/receipts` for compressed files that never got a row (an Android-local concern); web needs its own handling if an upload fails mid-flight.
- **Ties to:** ADR-0043 (SECURITY DEFINER partner-read storage RLS), the couple-banner bucket (v1.7.0 Item 10).

## W8 — Web app greenfield foundational design

- **Status:** BOOKED, greenfield, needs a full grill (the big one). Architecture *direction* decided 2026-07-28 (below); the grill still needs to pressure-test it and resolve what's still open. Likely spawns its own ADR(s) and possibly its own repo (or a monorepo with a new `shared` module — see W10).
- **The problem:** everything about the web client's shape is undecided — hosting, auth flows (email+password + Google OAuth *web* flow, email verification, session handling — the native app uses Credential Manager / `linkIdentityWithIdToken`, none of which apply on web), and the **sync-engine question**: offline-first (port the push/pull engine) vs. online-only-first (simpler, defer offline). **The sync-engine question is now answered — web v1 is online-only ([ADR-0063](../adr/0063-web-v1-is-online-only.md), 2026-08-03).** Hosting and auth flows remain open.
- **Locked direction (2026-07-28): share business logic via Kotlin Multiplatform; build the UI natively per platform.** Not a formal grill output — a conversation-level decision, recorded here so it isn't re-litigated from scratch next session; the grill should stress-test it, not re-derive it.
  - **Why:** the highest-stakes risk in this whole track isn't UI mismatch, it's *silent* divergence in sync/money/dedup logic (the entire reason [cross-platform-contract.md](cross-platform-contract.md) exists). Sharing the compiled Kotlin logic turns "the web client must reproduce this exactly" into "it's the same code" — eliminating the risk by construction instead of documenting it and hoping.
  - **Why it's tractable for this codebase specifically:** the domain layer already follows "zero Android imports" as a house architecture rule (CLAUDE.md), originally for JVM-only fast unit tests — several files (`NoteCharLimit`, `NoteContentText`, and by the same pattern likely `RecurringScheduler` and the money-math usecases) are already written in `commonMain`-compatible style, not by luck. **Correction (2026-08-03, W2 grill): `DeterministicUuid` is NOT one of them** — it is Android-free but JVM-bound, built on `java.nio.ByteBuffer`, `java.security.MessageDigest`, and `java.util.UUID`, none of which exist on a Kotlin/JS target. Moving it is a **rewrite onto different SHA-1 and UUID primitives**, and it is simultaneously the highest-stakes file in the extraction (a byte-order slip silently yields different ids, so duplicated rows instead of merged ones). Treat "zero Android imports" as necessary but **not sufficient** evidence of portability — audit each candidate file for JVM-only types before assuming it moves cleanly. `supabase-kt` — already the chosen backend client — is itself Kotlin Multiplatform (Android + JS/Wasm targets), so the remote-source layer doesn't need a TypeScript rewrite either.
  - **What moves to `shared` (Kotlin/JS target, not Wasm — this is headless logic, not rendering, so Kotlin/JS's maturity + clean TS interop via `@JsExport` wins over Wasm):** domain models, usecases, repository interfaces, the Supabase remote sources/DTOs/mappers, the sync engine (push/pull, LWW, `server_rev` cursor), deterministic-id generation (§1/§1b of the contract), money math (§4). One real swap needed: `java.math.BigDecimal` → a KMP decimal library (`ionspin/kotlin-bignum`) in the shared module, since `BigDecimal` is JVM-only.
  - **What stays platform-specific (correctly):** Room, DataStore, WorkManager stay Android-only; web's UI is hand-built. **Web has no local persistence layer at all under [ADR-0063](../adr/0063-web-v1-is-online-only.md)** (online-only v1) — it reads and writes Supabase directly through the shared repositories, so the "if it goes offline-first" caveat is resolved rather than open. A browser tab and an Android background service are different execution environments — sharing those would be false symmetry, not a real win. The atomic-multi-row-write question ([contract §9](cross-platform-contract.md#9-atomic-multi-row-writes--android-has-a-primitive-web-doesnt)) is unaffected by this decision either way — Room's transaction primitive doesn't cross to web regardless of shared logic elsewhere.
  - **Forward-compatible with the iOS longer-horizon:** the same `commonMain` module extends to an `iosMain` (Kotlin/Native) target later with no redo, *if* it's built with clean `expect`/`actual` boundaries and multiplatform-safe types from the start (`kotlinx-datetime` not `java.time`, `kotlin-bignum` not `java.math.BigDecimal`). No iOS-specific work needed now — no Mac/Xcode toolchain exists yet, and UI-sharing (Compose Multiplatform, more credible for Android⇄iOS than Android⇄Web since both are native touch-app mediums) is a separate, later decision.
  - **UI layer:** native per platform, not shared. Web UI is hand-built React/Tailwind/shadcn (unaffected by this decision — see the surviving stack notes below), consuming the shared module for all business logic + data access.
- **Open tensions still to grill:** ~~offline-first vs. online-first for web v1~~ — **RESOLVED 2026-08-03 → online-only ([ADR-0063](../adr/0063-web-v1-is-online-only.md))**: the phone stays the offline surface, the browser is the desk surface, and browser-local storage plus a sync layer is one of the largest chunks in the whole web build for a use case that barely exists. Not a one-way door — the sync logic is shared, so offline is additive later, not a rewrite. Still open: exact `shared` module boundaries (which usecases move vs. stay ViewModel-adjacent); build/CI tooling for a Kotlin/JS artifact consumed by a separate npm-based web repo (published package vs. monorepo); how much of this needs a formal ADR vs. living in this doc.
- **Depends on:** W1–W6 being settled (they shape the schema the shared module reads/writes); **W10** (the actual extraction, separately scheduled).

### Web-app surface notes (UI layer only — unaffected by the W10 shared-module decision)

The UI/framework choice below is still relevant regardless of the shared-logic decision, since only the *logic* moves to Kotlin — the web UI itself is still hand-built:

| Layer | Pick | Why for this app |
|---|---|---|
| Framework | **Next.js (React)** | Best Supabase integration + AI-assist support; serves SEO marketing/legal pages (SSG) + the app shell in one project. Consumes the `shared` Kotlin/JS module for all domain/sync/money logic — this repo owns UI + wiring only. |
| Styling / UI | **Tailwind CSS + shadcn/ui** (Radix primitives) | Playful Pop is bespoke — a pre-styled lib (MUI) would fight it; shadcn gives unstyled, accessible components restyled to brand tokens. |
| Server state | **TanStack Query** | Wraps calls into the shared module's repositories — mirrors the StateFlow observe+refresh model, now backed by shared Kotlin instead of a parallel TS data layer. |
| Auth | `@supabase/supabase-js` + `@supabase/ssr` (or the shared module's Supabase client, if auth logic also moves in) | **Google SSO on web is a redirect OAuth flow, not Credential Manager** — ADR-0050 is Android-only, different code path, same Supabase identity. |
| Charts | **Recharts** or **visx** | For the Analysis donut / expense-flow (hand-rolled in Compose Canvas natively). |
| Hosting | **Vercel** or **Cloudflare Pages**, edge near **ap-southeast-1** | Supabase stays the backend (Singapore, good PH latency). |
| PWA | Service worker (Vite-PWA / next-pwa) | Installable app-shell. |

**Superseded by the KMP decision (kept here only as a record of what NOT to do):** the earlier draft of this section recommended `decimal.js`, a `uuid` v5 npm package, and hand-porting the sync engine onto Dexie/IndexedDB — all now unnecessary for whatever moves into `shared`, since that logic is literally reused, not reimplemented. The earlier advice to avoid third-party sync frameworks (ElectricSQL, PowerSync, RxDB) still stands, for the same underlying reason: the sync protocol is already defined and shouldn't be replaced by a framework with its own opinions.

## W9 — Evaluate server-side notification generation (explicitly deferred by ADR-0053)

- **Status:** BOOKED, needs grill/decision. Model TBD. **Source: this isn't inferred — [ADR-0053](../adr/0053-notification-inbox-synced-source-of-truth.md) names this exact deferral itself:** *"Fully synced but server-generated (an edge function emits events, all clients read one list) — the 'correct' long-term multi-client design, but a large backend lift; deferred to the web-app build."*
- **Context:** the notification inbox (v1.7.1 Item 6, built 2026-07-27) was deliberately built **synced now** — its own ADR states this explicitly *because* the web app is imminent (see [cross-platform-contract.md §1b](cross-platform-contract.md#1b-notification-inbox-composite-ids--a-second-distinct-scheme--built--live-v171-item-6--adr-0053), ✅ already live: Room v30, migration #22, `notifications` table, own-user-only, no partner variant). Client-side deterministic composite ids (`budget:{id}:{month}:{slot}`, `recurring:{occurrenceId}`, `debt:{debtId}`) already give most of server-generation's dedup benefit *without* a backend — which is why it shipped client-generated first rather than waiting.
- **The actual question for this item:** does the web app (a) just **adopt the existing client-generated scheme** — reproduce the same id formats + create-if-absent write pattern in TypeScript (cheap, no backend change, consistent with W2's general approach) — or (b) become the trigger to finally move generation **server-side** via an edge function (the "correct" design ADR-0053 named but declined to build early)?
- **Leans toward (a) for the initial web launch:** cheaper, no new Supabase infra, and directly continues the pattern the ADR already validated. **(b) becomes worth revisiting** only if/when W3's recurring-materialization or budget-alert-evaluation questions independently justify standing up Supabase's first edge function + cron — at which point migrating notification generation onto the same infra is a small marginal add, not a separate project.
- **Ties to:** [W2 §1b](cross-platform-contract.md#1b-notification-inbox-composite-ids--a-second-distinct-scheme--built--live-v171-item-6--adr-0053), [W3](#w3--recurring-materialization--notification-evaluation-server-side-vs-web-reimplementation), ADR-0053.

## W10 — Extract domain/data/sync layer into a Kotlin Multiplatform `shared` module

- **Status:** BOOKED — the concrete build work behind W8's locked architecture direction. **Not scheduled now.** No code change needed today; this is deliberate prep that should start as its own dedicated slice **closer to when the web build actually begins**, not scattered into the current native batch — matches CLAUDE.md's own rule against building for hypothetical future requirements, and there's nothing yet to consume the module. Model/effort TBD at booking time (likely Opus — cross-cutting module boundary work, new build tooling, real risk of subtly breaking existing Android behavior mid-extraction).
- **What it is:** stand up a `shared` Gradle module with Android + Kotlin/JS targets (`iosMain` added later, not now); incrementally move the domain layer's usecases, repository interfaces, Supabase remote sources/DTOs/mappers, and the sync engine into `commonMain`; swap `java.math.BigDecimal` → `kotlin-bignum`, `java.time` → `kotlinx-datetime`, and — **added 2026-08-03** — `java.security.MessageDigest` / `java.util.UUID` / `java.nio.ByteBuffer` → multiplatform SHA-1, UUID, and byte-handling equivalents in `DeterministicUuid`; leave Room/DataStore/WorkManager and all UI as Android-only `androidMain` implementations of the shared interfaces.
- **Suggested phasing (once scheduled):**
  1. Empty module + Kotlin/JS target wired into the build — no behavior change, pure plumbing, low risk.
  2. Migrate the highest-stakes pieces first: `DeterministicUuid` and its call sites, `RecurringScheduler`, the money-derived usecases (balance, budget %, `DebtAllocationCalculator`, netting), the LWW/sync engine — exactly the surfaces where drift is silent and expensive per [cross-platform-contract.md](cross-platform-contract.md). **Hard precondition (W2 grill, 2026-08-03): the conformance vectors must already exist and pass before this phase starts.** `DeterministicUuid` is a rewrite here, not a move (see the W8 correction), so these vectors are the only mechanism that would catch the rewrite silently changing generated ids. Phase 1 above is safe to run before the vectors land; this phase is not.
  3. Leave ViewModel-shaped state logic out — that's legitimately different between Compose and React and shouldn't be forced together.
- **The one thing worth doing *now*, informally, at zero extra cost:** nothing new — CLAUDE.md's existing "domain layer has zero Android imports" rule already produces exactly the code shape this extraction needs. No new discipline required going forward, just don't let it slip on new features (e.g. whatever ADR-0057 introduces) while this sits unscheduled.
- **Ties to:** W2 (this is *why* W2's role shrunk), W8, the iOS longer-horizon consideration (build `commonMain` with clean `expect`/`actual` boundaries so an `iosMain` target is additive later, not a redo).
