Lesson 01

Sonnet or Opus?
The One Decision That Changes Everything

Mission: Make model decisions automatically on Ipon, Love — without consulting CLAUDE.md every time.

The Framework

Every task in Ipon, Love falls into one of two categories. Knowing which category a task belongs to tells you which model to use.

Pattern task → Sonnet
You have already solved this class of problem. At least one reference feature exists in the codebase. The work is: copy the pattern, adapt the names and schema, wire it up. Sonnet executes this reliably and cheaply.
Design task → Opus
The design itself is unsolved. Multiple architectural decision records (ADRs) interact. Shared state between users is involved. Or you can't clearly picture the answer before writing the first line of code. Opus reasons through multi-step uncertainty better; Sonnet will pattern-match its way to the wrong design.

The signal checklist

Ask these questions before starting any slice. The first "yes" in the Opus column stops you — reach for Opus.

  • Sonnet A reference feature already exists in the codebase that I can copy from
  • Sonnet The task is additive to an existing screen or flow — nothing is redesigned
  • Sonnet CLAUDE.md explicitly calls this feature "low design risk"
  • Opus The design spans 3 or more ADRs simultaneously
  • Opus Shared state between partners is involved (replication, combined view, conflict resolution)
  • Opus A subtle concurrency or sync bug needs multi-step reasoning to diagnose
  • Opus I cannot picture what "done" looks like before writing the first line

One more rule: when to run /grilling first

The model choice and the pre-build investment are separate decisions. If you are reaching for Opus, run /grilling first — stress-test the design before writing code. If you are reaching for Sonnet but something feels slightly off, a quick /grilling still costs less than rework.

A design task that skips /grilling is the most common source of rework in this project.
